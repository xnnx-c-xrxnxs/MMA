Contracts & Types

How Zod schemas enforce runtime validation, provide TypeScript types, and isolate domains through per-domain packages. The contracts packages are the published language shared between services.

Why Shared Contracts Packages?

Domain entities are internal to each domain package — they never cross service boundaries. The contracts packages define the public API surface: input validation schemas, response shapes, and event payloads. This gives us:

  • Runtime validation — Zod schemas parse every API input (via ZodValidationPipe) and every API output (via schema.parse() in the Application Service).
  • TypeScript types for free — z.infer<typeof schema> generates types directly from schemas. No manual interface files.
  • Domain isolation — per-domain packages ensure a type error in the order domain doesn't break the user service at compile time.

Domain-Scoped Imports (Domain Isolation)

Each domain has its own independent package with its own package.json and dependencies. There is no root @old-st/contracts package — only per-domain packages.

tsconfig.base.json defines path aliases so TypeScript resolves @old-st/contracts/{domain} to the correct per-domain package: 

// tsconfig.base.json (paths)
"@old-st/contracts/common":  ["packages/contracts/common/src/index.ts"],
"@old-st/contracts/user":    ["packages/contracts/user/src/index.ts"],
"@old-st/contracts/order":   ["packages/contracts/order/src/index.ts"],
"@old-st/contracts/product": ["packages/contracts/product/src/index.ts"],
"@old-st/contracts/auth":    ["packages/contracts/auth/src/index.ts"]
Golden Rule #11 — Never import from the bare @old-st/contracts root. Always use domain-scoped subpath imports. The root barrel creates transitive type coupling — a type error in any domain will break every consumer.

Correct vs Incorrect Import

// ✅ Correct — domain-scoped, isolated
import { createUserSchema, UserResponse } from '@old-st/contracts/user';
import { orderResponseSchema } from '@old-st/contracts/order';
import { PaginatedResponse } from '@old-st/contracts/common';

// ❌ Wrong — transitive coupling
import { createUserSchema, orderResponseSchema } from '@old-st/contracts';

Step 1 — Domain Constants (Source of Truth)

Enums and allowed values are defined once in the domain package:

// packages/user-domain/src/domain/constants/user-status.constant.ts
export const USER_STATUSES = ['PENDING', 'ACTIVE', 'INACTIVE', 'DELETED'] as const;
export type UserStatus = (typeof USER_STATUSES)[number];
export const UserStatusEnum = {
  PENDING: 'PENDING',
  ACTIVE: 'ACTIVE',
  INACTIVE: 'INACTIVE',
  DELETED: 'DELETED',
} as const;

Step 2 — Zod Schema (Contracts Package)

Contracts re-export the domain constants and build Zod schemas from them:

// packages/contracts/user/src/schemas.ts
import { USER_ROLES, USER_STATUSES, UserRoleEnum, UserStatusEnum } from '@old-st/user-domain';

// Re-export for consumers
export { USER_ROLES, USER_STATUSES, UserRoleEnum, UserStatusEnum };

// Build Zod enum from domain constant
export const userStatusSchema = z.enum(USER_STATUSES);

// Compose into larger schemas
export const userResponseSchema = z.object({
  userId: z.string(),
  email: z.string().email(),
  firstName: z.string(),
  lastName: z.string(),
  userRole: userRoleSchema,
  userStatus: userStatusSchema,
  data: userDataSchema,
  dateCreated: z.string().datetime(),
  updatedAt: z.string().datetime(),
});

Step 3 — TypeScript Types (Inferred)

Types are never written manually — they're inferred from Zod schemas:

export type UserResponse = z.infer<typeof userResponseSchema>;
// Equivalent to:
// {
//   userId: string;
//   email: string;
//   firstName: string;
//   lastName: string;
//   userRole: 'USER' | 'ADMIN';
//   userStatus: 'PENDING' | 'ACTIVE' | 'INACTIVE' | 'DELETED';
//   data: { country?: string };
//   dateCreated: string;
//   updatedAt: string;
// }

  • Input validation: ZodValidationPipe in the presentation layer parses and validates request bodies, query parameters, and route parameters.
  • Output validation: The Application Service calls schema.parse() to transform domain entities into DTOs. This ensures the response shape matches the contract, and strips any unintended properties.
  • No toObject() (Golden Rule #13): Entities never serialize themselves. The Application Service manually reads getters and passes them to schema.parse().

Event Schemas (Discriminated Unions)

Each domain's event-schemas.ts defines a Zod discriminated union keyed on eventType. This enables type-safe event dispatch in SQS consumers.

How Discriminated Unions Work

// packages/contracts/product/src/event-schemas.ts
export const productDomainEventSchema = z.discriminatedUnion('eventType', [
  productDeactivatedSchema,     // { eventType: 'PRODUCT_DEACTIVATED', productId, occurredAt }
  productDiscontinuedSchema,    // { eventType: 'PRODUCT_DISCONTINUED', ... }
  productDeletedSchema,         // { eventType: 'PRODUCT_DELETED', ... }
  productPriceChangedSchema,    // { eventType: 'PRODUCT_PRICE_CHANGED', productId, oldPrice, newPrice, ... }
  productValidationSucceededSchema, // { eventType: 'PRODUCT_VALIDATION_SUCCEEDED', orderId, ... }
  productValidationFailedSchema,    // { eventType: 'PRODUCT_VALIDATION_FAILED', orderId, reason, failedProducts, ... }
]);

// In the event handler service:
const parsed = productDomainEventSchema.parse(rawPayload);
switch (parsed.eventType) {
  case 'PRODUCT_PRICE_CHANGED':
    // TypeScript knows: parsed.oldPrice, parsed.newPrice exist
    break;
  case 'PRODUCT_VALIDATION_FAILED':
    // TypeScript knows: parsed.reason, parsed.failedProducts exist
    break;
}

Pagination Schemas

The @old-st/contracts/common subpath provides two pagination helpers, matching each persistence strategy:

StrategyUsed ByResponse TypeKey Fields
Cursor-based User, Product (DynamoDB) PaginatedResponse<T> data, nextCursorPointer, prevCursorPointer
Offset-based Order (Prisma) OffsetPaginatedResponse<T> data, total, page, limit, totalPages 
// Cursor-based (DynamoDB)
import { PaginatedResponse, createPaginatedResponse } from '@old-st/contracts/common';

const result: PaginatedResponse<UserResponse> = createPaginatedResponse(
  users, nextCursor, prevCursor
);

// Offset-based (Prisma)
import { OffsetPaginatedResponse, createOffsetPaginatedResponse } from '@old-st/contracts/common';

const result: OffsetPaginatedResponse<OrderResponse> = createOffsetPaginatedResponse(
  orders, totalCount, page, limit
);

Adding Contracts for a New Domain

  1. Create packages/contracts/{domain}/ directory with package.json, project.json, and tsconfig.json.
  2. Create packages/contracts/{domain}/src/schemas.ts — import domain constants, create Zod schemas, infer types.
  3. Create packages/contracts/{domain}/src/event-schemas.ts — import event type enum, create per-event Zod schemas, build discriminated union.
  4. Create packages/contracts/{domain}/src/index.ts — re-export both files.
  5. Add path alias to tsconfig.base.json: "@old-st/contracts/{domain}": ["packages/contracts/{domain}/src/index.ts"]
  6. Run pnpm install from the workspace root to link the new package.
Each domain is an independent package. There is no root barrel to update. New domains are fully isolated — they cannot introduce transitive type coupling.
