Monitoring & Observability

Structured JSON logging via @mma/telemetry, request-scoped correlationId propagation, the internal monitoring-api-service, and CloudWatch dashboards. All services emit correlated log lines — every line carries a correlationId so logs from HTTP requests and SQS event chains are joinable in CloudWatch Log Insights.

Locally, initTelemetry() is a no-op (OTEL_SDK_DISABLED=true in .env.local) — no X-Ray daemon or OTel collector is needed. Logs are still emitted as structured JSON to stdout, which means you can parse them locally with jq or search them in your terminal.

The @mma/telemetry Package

Located at packages/telemetry/. Exports five main things:

ExportPurpose
initTelemetry(serviceName) Bootstraps the OpenTelemetry SDK (OTLP exporter → X-Ray). No-op when OTEL_SDK_DISABLED=true. Must be called before NestFactory.create() in main.ts.
createLogger(serviceName): StructuredLogger Returns a structured JSON logger. Emits one JSON line per call to process.stdout. Each line includes timestamp, level, service, message, correlationId, plus any extra fields you pass. When an active OTel span exists, traceId and spanId are added automatically.
correlationMiddleware() Express middleware that generates a UUID correlationId per HTTP request (or reuses x-correlation-id from incoming headers). Stores it in AsyncLocalStorage so the logger and SQS publishers can read it automatically. Must be the first middleware in setupGlobalMiddleware().
runWithCorrelationId(id, fn) / getCorrelationId() runWithCorrelationId wraps an async function in a correlation context. Used by event handlers to restore the correlationId from the SQS message body. getCorrelationId() reads the current correlationId from AsyncLocalStorage — used by SQS publishers to auto-inject it into event payloads.
getCorrelationHeaders() Returns { 'x-correlation-id': id } if a correlation context is active, or {} otherwise. Spread into outbound HTTP request headers in ACL adapters so the receiving service continues the same correlationId chain.
injectTraceContext / extractTraceContext Propagates W3C trace context through SQS MessageAttributes. Used by event publishers (inject) and SQS consumer services (extract).

Structured Log Format

Every log call produces a single-line JSON object:

{
  "timestamp": "2026-04-16T10:23:45.123Z",
  "level": "INFO",
  "service": "user-api-service",
  "message": "User created",
  "traceId": "1-661e2b21-abc123def456...",
  "spanId": "a1b2c3d4e5f60011",
  "correlationId": "a3f2c8d1-7e4b-4f9a-b6c2-1d8e5f0a3b7c",
  "userId": "usr_abc",
  "email": "user@example.com"
}

The correlationId is the primary correlation mechanism. It is generated per HTTP request by correlationMiddleware(), auto-injected into SQS event payloads by the publishers, and extracted by event handlers via runWithCorrelationId(). This creates end-to-end request tracing across HTTP → SQS → event handler chains without depending on X-Ray. The monitoring dashboard groups all logs sharing the same correlationId into a single "event chain".

Error calls additionally include errorType, errorMessage, and stack:

logger.error('Failed to create user', { email }, someError);
// → { ..., "errorType": "DuplicateEmailError", "errorMessage": "...", "stack": "..." }

Using createLogger()

Golden Rule

Never use new Logger(ClassName.name) from @nestjs/common. Always declare a module-level singleton: 

import { createLogger } from '@mma/telemetry';

const logger = createLogger('user-api-service');   // top of the file, outside the class

@Injectable()
export class UserApplicationService {
  async createUser(input: CreateUserInput): Promise<UserDto> {
    logger.info('Creating user', { email: input.email, userRole: input.userRole });
    const user = await this.createUserUseCase.execute(input);
    logger.info('User created', { userId: user.id, email: user.email });
    return userResponseSchema.parse(user);
  }
}

Log Levels

SituationLevelMethod
Operation start / completionInfologger.info(...)
Non-fatal unexpected conditionWarnlogger.warn(...)
Domain exception caught by filterWarnlogger.warn(...)
Unhandled 5xx, infrastructure failureErrorlogger.error(...)
Detailed debugging (rarely committed)Debuglogger.debug(...)

What to Log

  • Before a mutating operation — what is being done + key input identifiers (userId, productId, etc.)
  • After success — confirming completion + result identifier
  • Before publishing an event — note the event type being dispatched
  • Before and after ACL calls — outbound cross-service HTTP validation calls (e.g. customerValidator.validate()) must have before/after logs in the adapter so the call appears in the event chain
  • Read endpoints called by ACL — when a read method (e.g. getUserById) is the target of another service's ACL call, it must have before/after logs so the upstream service appears in the monitoring event chain
  • On error — pass the error object as the third argument to logger.error()
  • Never log passwords, tokens, full PII, or raw request bodies

Mutating operations include: create, update, delete, activate, deactivate, verify, state transitions, event publishing, sign-in/sign-out, password changes, and presigned URL generation. Read-only operations (getById, list, search) do not require before/after logs unless the endpoint is called by another service's ACL adapter — in that case, logs are required so the upstream service appears in the event chain.

CI Enforcement

The app-service-has-logger structural lint check (in scripts/lint-standards.ts) runs in CI and verifies that every application service file has a module-level const logger = createLogger(...) declaration. It also detects and rejects the forbidden new Logger() pattern from @nestjs/common. A PR that adds an application service without a structured logger will fail CI.

OTel Initialisation in main.ts

Every service's main.ts must call initTelemetry() before NestFactory.create(). This registers the OTel SDK so that spans are active when the NestJS request lifecycle begins — ensuring traceId and spanId are available to every logger call inside the request. 

import { initTelemetry } from '@mma/telemetry';

initTelemetry('user-api-service');   // ← must be FIRST, before NestFactory

async function bootstrap() {
  const app = await NestFactory.create(AppModule);
  // ...
}
bootstrap();

Lambda Web Adapter requires no special bootstrap — your main.ts starts a plain NestJS HTTP server inside the Lambda container. Just call initTelemetry() at module load (outside any handler), so it runs once at cold start.

Local Dev: OTel Disabled

.env.local sets OTEL_SDK_DISABLED=true. This makes initTelemetry() a no-op — no OTel collector, no X-Ray daemon, no network calls. Logs still emit as structured JSON to stdout; they just won't carry traceId/spanId values.

Dependency Setup

HTTP API Services (no own package.json)

@mma/telemetry is declared in the workspace root package.json. No per-service action needed — imports resolve automatically.

Event-Handler Services (own package.json)

Add to the service's package.json dependencies: 

"@mma/telemetry": "workspace:*"

Monitoring Service

apps/monitoring/monitoring-api-service/ is an internal NestJS service that aggregates observability data from AWS and exposes it to the monitoring dashboard. It runs on port 8080 locally and uses the Lambda Web Adapter pattern in deployed environments (plain HTTP server — no @codegenie/serverless-express).

Controllers

ControllerRouteWhat it does
TracesController GET /api/traces
GET /api/traces/:correlationId		 Lists recent event chains (grouped by correlationId) with description, services involved, log count, duration, and status. Detail endpoint returns all correlated log entries for a specific chain.
AlarmsController GET /api/alarms Lists CloudWatch alarms filtered by name prefix for the target environment. Optional state filter (OK | ALARM | INSUFFICIENT_DATA).
ServicesController GET /api/services Returns recent X-Ray service map — service names, error rates, response times.
AuthController POST /api/auth/sign-in Internal auth for the monitoring dashboard. Issues a short-lived session token (stored in localStorage — internal tool only).
AppController GET /api/health Health check — returns { status: 'ok', service: 'monitoring-api-service' }.

Multi-Environment Support

The monitoring service accepts an X-Target-Environment request header (values: dev, staging, prod). The monitoring webapp passes the currently selected environment via this header, so a single deployed monitoring service can query CloudWatch and X-Ray for any environment.

Authentication

All monitoring API routes (except /api/health and /api/auth/sign-in) require a Bearer token issued by the internal AuthController. This is a lightweight internal auth mechanism — not the same Cognito/LocalAuth flow used by domain API services. The monitoring webapp stores the token in localStorage; this is acceptable because the monitoring dashboard is an internal developer tool, never user-facing.

Monitoring Dashboard (monitoring-webapp)

A Next.js app at apps/monitoring/monitoring-webapp/ running on port 4300. It is a developer-facing internal tool, not deployed as part of the public product stack.

Dashboard Pages

Dashboard / Summary cards — alarm counts (ALARM / OK), recent error traces, service health overview
Traces /traces Event chain list grouped by correlationId \u2014 shows description (derived from first log message + event types), services involved, log count, duration, and error status. Click-through to chain detail view with service flow diagram and correlated log timeline.

Environment Switching

Append ?env=staging (or prod, dev) to any page URL to view data from a different environment. The dashboard passes the selected env to the monitoring API via the X-Target-Environment header.

CloudWatch Alarms

The infra/modules/monitoring/ Terraform module creates two alarm types per service automatically:

Alarm typeMetricThresholdConfig needed
Lambda error alarm AWS/Lambda > Errors > lambda_error_threshold in 5 min Add function name to lambda_functions map in module.monitoring
SQS DLQ alarm AWS/SQS > ApproximateNumberOfMessagesVisible > 0 Add DLQ name to dlq_arns map in module.monitoring

When adding a new service, update lambda_functions and dlq_arns in all four environment roots (dev, staging, prod, preview). See the add-monitoring skill for the exact Terraform snippet. Preview environments use enable_alarms = false — alarm resources are never created for previews, so the maps can still be populated for consistency.

Notifications (SNS + AWS Chatbot)

Alarms publish to a per-environment SNS topic created by the infra/modules/notifications/ module. The topic fans out to:

  • Email subscriptions — declared in infra/notification-config.json. Each subscriber receives an SNS confirmation email on first deploy.
  • AWS Chatbot Slack channel(s) — declared in the same config file. Requires a one-time Slack workspace OAuth handshake in the AWS Chatbot console.

See docs/notifications.md for the full setup walkthrough, including first-time channel handshake and adding new channel types (PagerDuty, Opsgenie, MS Teams). Use the add-notifications skill or /add-alerting prompt to add a new channel.

CloudWatch Log Insights Queries

Useful queries for the CloudWatch Log Insights console:

All errors across all services (last 1 hour)

fields @timestamp, level, service, message, errorType, errorMessage, traceId
| filter level = "ERROR"
| sort @timestamp desc
| limit 50

Find all logs for a specific trace

fields @timestamp, level, service, message
| filter correlationId = "a3f2c8d1-7e4b-..."
| sort @timestamp asc

List recent event chains (correlationId grouping)

fields @timestamp, level, service, message, correlationId
| filter ispresent(correlationId)
| stats count() as logCount, min(@timestamp) as firstSeen, max(@timestamp) as lastSeen by correlationId
| sort firstSeen desc
| limit 50

Error rate by service (last 24 hours)

fields service, level
| filter level = "ERROR"
| stats count() as errorCount by service
| sort errorCount desc

Slow operations (warn about high latency)

fields @timestamp, service, message, durationMs
| filter ispresent(durationMs) and durationMs > 1000
| sort durationMs desc
| limit 20

The monitoring service requires AWS credentials to query CloudWatch and X-Ray. For local development pointing at a real AWS environment:

  1. Set AWS_PROFILE or AWS_ACCESS_KEY_ID / AWS_SECRET_ACCESS_KEY in your shell.
  2. Set X_TARGET_ENV_DEFAULT=dev (or whichever environment you want to inspect).
  3. Open http://localhost:4300 and sign in with the monitoring admin credentials.

Adding Monitoring to a New Service

When you add a new domain service, three steps are needed — use the add-monitoring Claude Code skill which covers all three:

  1. Terraform — add the Lambda function name to lambda_functions and (if it has an SQS queue) the DLQ name to dlq_arns in all four environment root module.monitoring blocks.
  2. initTelemetry() — call it in main.ts before NestFactory.create().
  3. correlationMiddleware() — for HTTP API services, add app.use(correlationMiddleware()) as the first middleware in setupGlobalMiddleware(). For event handler services, extract correlationId from the raw SQS body and wrap processing in runWithCorrelationId().
  4. createLogger() — add module-level logger singletons to the application service, exception filter, event handler, and any ACL clients. Log meaningful before/after messages at every domain operation. The logger automatically includes correlationId in every log line.
  5. Event schemas — if the service publishes SQS events, ensure all event schemas include correlationId: z.string().optional(). The SQS publisher auto-injects the correlationId — no manual work is needed in the publishing code.
