Persistence Patterns

The template supports two persistence strategies — DynamoDB OneTable (User, Product) and Prisma + PostgreSQL (Order). The domain and application layers are persistence-agnostic; only the infrastructure layer knows which database is in use.

Choosing a Persistence Layer

DynamoDB OneTable Prisma + PostgreSQL
Best for Single-table design, high-throughput key-value access, serverless-first Relational data, complex joins, aggregates, ACID transactions
Pagination style Cursor-based (IPaginatedResponse) Offset-based (IOffsetPaginatedResponse)
Local infrastructure LocalStack (DynamoDB on port 4566) Docker PostgreSQL (port 5432)
Schema location infrastructure/schemas/{Entity}Schema.ts infrastructure/prisma/schema.prisma
Migration Schema changes → update setup-localstack.ts → pnpm run localstack:setup:force npx prisma migrate dev --name describe_change
Used by User, Product Order
Never mix pagination styles within a domain. If a domain uses DynamoDB, all its list endpoints return cursor-based results. If it uses Prisma, all endpoints return offset-based results.

The Repository Pattern

Every domain defines a repository interface in the application layer. The infrastructure layer provides the implementation. This is dependency inversion — the domain dictates what operations exist; infrastructure decides how to fulfill them.

Key patterns in every repository

  • toDomain(record) — Converts a database record (DynamoDB item or Prisma row) into a domain entity using Entity.reconstitute(). This is private to the repository.
  • toPersistence(entity) — Converts a domain entity back to the database format using entity getters. Also private.
  • The domain never sees database types. No Prisma types, no OneTable model types leak out of the repository.
  • Repositories may define local structural interfaces to avoid OneTable generic type explosions or Prisma generated-type leaking.

DynamoDB OneTable Pattern

packages/user-domain/src/infrastructure/

Schema Design

OneTable uses a single-table design with typed models. Each entity defines its primary key (PK/SK) and Global Secondary Indexes (GSIs) using value templates:

// Simplified example — UserSchema
{
  pk:     { type: String, value: 'USER#\${userId}' },
  sk:     { type: String, value: 'USER#\${userId}' },
  GSI1pk: { type: String, value: 'EMAIL#\${email}' },     // Email lookup
  GSI1sk: { type: String, value: 'USER' },
  GSI4pk: { type: String, value: 'STATUS#\${userStatus}' }, // List by status
  GSI4sk: { type: String, value: '\${dateCreated}' },       // Sort by date
}

Cursor-Based Pagination

DynamoDB uses exclusive start keys for pagination. The repository wraps this in IPaginatedResponse:

interface IPaginatedResponse<T> {
  data: T[];
  nextCursorPointer: CursorPointer; // null = no more pages
  prevCursorPointer: CursorPointer; // null = first page
}

// CursorPointer is Record<string, unknown> | null
// It's opaque to the consumer — only the repository knows the internal key structure

In the API, clients pass ?cursor=...&direction=next or ?cursor=...&direction=prev. The application service routes the cursor to the correct pointer based on direction.

DynamoDB Config

One DynamoDB client per process (singleton). Multiple tables supported via DynamoDBConfig.getTable(name, schema). Local routing uses STAGE === 'local' as the primary check, with DYNAMODB_ENDPOINT as an explicit override.

Prisma + PostgreSQL Pattern

packages/order-domain/src/infrastructure/

Schema Design

Prisma uses a schema.prisma file with models, enums, and relations:

// Simplified example — Order schema
model Order {
  orderId     String       @id @default(uuid())
  customerId  String
  orderStatus OrderStatus  @default(DRAFT)
  totalAmount Float        @default(0)
  dateCreated DateTime     @default(now())
  updatedAt   DateTime     @updatedAt
  items       OrderItem[]
  payment     OrderPayment?

  @@index([customerId])
  @@index([orderStatus])
  @@map("orders")
}

enum OrderStatus {
  DRAFT
  PENDING
  CONFIRMED
  // ... mirrors domain constants exactly
}

Key Prisma Rules

  • Enums must mirror domain constants exactly (Golden Rule #17). The domain constants are the source of truth — the Prisma schema copies them.
  • Use @id @default(uuid()) for primary keys.
  • Use @default(now()) for dateCreated and @updatedAt for updatedAt.
  • Use @@map("table_name") for snake_case table names.
  • Cascade delete: set onDelete: Cascade on child models so deleting the parent cleans up children.
  • Add @@index on fields used in WHERE clauses.

Offset-Based Pagination

interface IOffsetPaginatedResponse<T> {
  data: T[];         // Items for the current page
  total: number;     // Total matching records
  page: number;      // Current page (1-based)
  limit: number;     // Items per page
  totalPages: number; // Calculated ceiling
}

The repository implements this with skip/take and a parallel count() query:

const [records, total] = await Promise.all([
  this.prisma.order.findMany({
    where: { orderStatus: status },
    skip: (page - 1) * limit,
    take: limit,
    include: { items: true, payment: true },
  }),
  this.prisma.order.count({ where: { orderStatus: status } }),
]);

Aggregate Saves with $transaction

Orders are aggregate roots with items and payment. Saving creates/updates all in a single transaction: 

await this.prisma.$transaction(async (tx) => {
  const orderRecord = await tx.order.upsert({ ... });
  // Delete removed items, upsert remaining items
  for (const item of entity.getItems()) {
    await tx.orderItem.upsert({ ... });
  }
  // Upsert payment if present
  if (entity.getPayment()) {
    await tx.orderPayment.upsert({ ... });
  }
});

Prisma Config

One Prisma client per process (singleton). PrismaConfig.getClient() reads {DOMAIN}_DATABASE_URL from env. The generated client lives at infrastructure/generated/client/ (gitignored) and is re-exported via the domain package's infrastructure barrel.

Migration Workflow

# Create a new migration (dev only)
npx prisma migrate dev --name describe_change

# Regenerate client after schema changes
npx prisma generate

# Apply all pending migrations (used by CI and local setup)
npx prisma migrate deploy

Data Mapping: Domain ↔ Database

All data mapping happens in the repository's private methods. The entity and the database format are kept strictly separate:

Timestamp Mapping

Domain EntityDynamoDBPrisma
dateCreated Mapped from OneTable's auto-managed createdAt Mapped from @default(now()) column
updatedAt Mapped from OneTable's auto-managed updatedAt Mapped from @updatedAt column
No createdAt on entities. Entities use dateCreated + updatedAt. The database may have a createdAt field (managed by the ORM), but the repository maps it to dateCreated when reconstituting the entity.

Wiring in the NestJS Module

Both persistence strategies are wired the same way — using provider tokens and factory providers:

DynamoDB Wiring

const DYNAMO_TABLE = 'DYNAMO_TABLE';
const USER_REPOSITORY = 'USER_REPOSITORY';

@Module({
  providers: [
    {
      provide: DYNAMO_TABLE,
      useFactory: () =>
        DynamoDBConfig.getTable(
          process.env.USERS_DYNAMODB_TABLE_NAME || 'OldSTTable',
          UserSchema,
        ),
    },
    {
      provide: USER_REPOSITORY,
      useFactory: (table: Table) => new DynamoUserRepository(table),
      inject: [DYNAMO_TABLE],
    },
    {
      provide: CreateUserUseCase,
      useFactory: (repo: IUserRepository) => new CreateUserUseCase(repo),
      inject: [USER_REPOSITORY],
    },
    // ... other use cases
    UserApplicationService,
  ],
})

Prisma Wiring

const PRISMA_CLIENT = 'PRISMA_CLIENT';
const ORDER_REPOSITORY = 'ORDER_REPOSITORY';

@Module({
  providers: [
    {
      provide: PRISMA_CLIENT,
      useFactory: () => PrismaConfig.getClient(),
    },
    {
      provide: ORDER_REPOSITORY,
      useFactory: (prisma: PrismaClient) => new PrismaOrderRepository(prisma),
      inject: [PRISMA_CLIENT],
    },
    {
      provide: CreateOrderUseCase,
      useFactory: (repo: IOrderRepository, validator: ICustomerValidator, publisher: IEventPublisher) =>
        new CreateOrderUseCase(repo, validator, publisher),
      inject: [ORDER_REPOSITORY, ICustomerValidator, EVENT_PUBLISHER],
    },
    // ... other use cases
    OrderApplicationService,
  ],
})

The pattern is identical — only the config class and client type differ. Use cases receive the repository interface, not the implementation.
