Event-Driven Architecture (SQS)

How SQS event-driven services consume messages from queues, with two runtime modes (local polling and AWS Lambda) sharing a single dispatcher.

Two Runtime Modes, One Codebase

Each event handler service ships as one codebase that runs in two different environments. The entry point (main.ts) branches on STAGE=local:

Key Components

NormalizedSqsRecord (Type Boundary)

The NormalizedSqsRecord interface is the type boundary between the infrastructure layer (AWS SDK types) and the application layer (pure TypeScript): 

// application/interfaces/normalized-sqs-record.interface.ts
export interface NormalizedSqsRecord {
  body: string;
  messageId?: string;
  receiptHandle?: string;
}

Both the Lambda handler and SqsLocalService normalize their respective message types into this interface before passing to the event handler service. This means the application layer has zero AWS SDK dependencies.

IEventHandler (Per-Event Contract)

// application/interfaces/event-handler.interface.ts
export interface IEventHandler<TPayload> {
  handle(payload: TPayload, messageId?: string): Promise<void>;
}

Each event type gets its own handler class implementing this interface.

Event Handler Application Service (Dispatcher)

The application service owns the dispatch logic — parse, switch, delegate:

// application/services/user-event-handler.service.ts
@Injectable()
export class UserEventHandlerService {
  constructor(
    private readonly userDeletedHandler: UserDeletedHandler,
  ) {}

  async handleRecords(records: NormalizedSqsRecord[]): Promise<void> {
    for (const record of records) {
      await this.processRecord(record);
    }
  }

  private async processRecord(record: NormalizedSqsRecord): Promise<void> {
    const parseResult = userDomainEventSchema.safeParse(
      JSON.parse(record.body)
    );

    if (!parseResult.success) {
      this.logger.error('Invalid event shape', parseResult.error.issues);
      return;  // skip — don't throw, don't requeue
    }

    switch (parseResult.data.eventType) {
      case UserEventTypeEnum.USER_DELETED:
        await this.userDeletedHandler.handle(
          parseResult.data, record.messageId
        );
        break;
      default:
        this.logger.warn(`Unhandled event type: ${...}`);
    }
  }
}
Parse failures skip, handler failures rethrow. If the Zod parse fails (unknown event shape), the record is logged and skipped — it won't requeue forever. If a handler throws, the error propagates up so the message is not deleted (local) or retried by Lambda (production).

SqsLocalService (Local Polling)

SqsLocalService is an @Injectable() NestJS service that polls LocalStack SQS in an infinite loop. It only runs when STAGE=local: 

// infrastructure/sqs/sqs-local.service.ts
@Injectable()
export class SqsLocalService {
  private readonly sqsClient = new SQSClient({
    region: process.env.DEFAULT_REGION || 'us-east-1',
    endpoint: process.env.LOCALSTACK_ENDPOINT,
    credentials: { accessKeyId: 'test', secretAccessKey: 'test' },
  });

  constructor(
    private readonly eventHandler: UserEventHandlerService,
  ) {}

  async pollQueue(): Promise<void> {
    const queueUrl = process.env.USERS_SQS_QUEUE_URL;
    while (true) {
      const { Messages } = await this.sqsClient.send(
        new ReceiveMessageCommand({
          QueueUrl: queueUrl,
          MaxNumberOfMessages: 10,
          WaitTimeSeconds: 20,
        })
      );
      for (const msg of Messages ?? []) {
        await this.processMessage(msg, queueUrl);
      }
    }
  }

  // Normalize → dispatch → delete on success
  private async processMessage(msg: Message, queueUrl: string) {
    const normalized: NormalizedSqsRecord = {
      body: msg.Body ?? '',
      messageId: msg.MessageId,
      receiptHandle: msg.ReceiptHandle,
    };
    await this.eventHandler.handleRecords([normalized]);
    await this.sqsClient.send(
      new DeleteMessageCommand({
        QueueUrl: queueUrl,
        ReceiptHandle: msg.ReceiptHandle,
      })
    );
  }
}

Publisher Wiring in NestJS Module

The publisher is injected into use cases via a token. The module factory creates the right client based on STAGE: 

// In the NestJS module:
const EVENT_PUBLISHER = 'EVENT_PUBLISHER';

{
  provide: EVENT_PUBLISHER,
  useFactory: () => {
    const queueUrl = process.env.{DOMAIN}_SQS_QUEUE_URL;
    const client = process.env.STAGE === 'local'
      ? createLocalSqsClient()
      : createAwsSqsClient();
    return new SqsStandardEventPublisher(client, queueUrl);
  },
},

// Use case receives it via factory:
{
  provide: CreateOrderUseCase,
  useFactory: (repo, validator, publisher) =>
    new CreateOrderUseCase(repo, validator, publisher),
  inject: [ORDER_REPOSITORY, ICustomerValidator, EVENT_PUBLISHER],
},
Event publishing happens in the use case, not the application service. This keeps the use case self-contained — it owns the complete operation (persist + publish) rather than splitting responsibility across layers.

Service Layout (Event Handler)

Event handler services have no HTTP server, no controllers, no Swagger:

apps/{domain}/{domain}-event-handler-service/
  src/
    main.ts                              ← dual-mode entry (local + Lambda)
    app/
      app.module.ts                      ← root module
    application/
      interfaces/
        normalized-sqs-record.interface.ts  ← type boundary
        event-handler.interface.ts          ← IEventHandler<T>
      services/
        {domain}-event-handler.service.ts   ← dispatch: parse → switch → delegate
        handlers/
          {event-name}.handler.ts           ← one class per event type
          index.ts                          ← barrel export
    infrastructure/
      config/                            ← optional (DynamoDB/Prisma if domain writes)
      sqs/
        sqs-local.service.ts             ← LocalStack polling (STAGE=local only)
    modules/
      {domain}.module.ts                 ← providers: handlers + event service + SqsLocalService

Key differences from HTTP API services:

  • No presentation/ folder (no controllers, pipes, or filters).
  • No port registration — event handlers don't listen on HTTP.
  • No Swagger — no @nestjs/swagger dependency.
  • main.ts uses NestFactory.createApplicationContext() instead of NestFactory.create().
  • Module has no controllers: array.

CorrelationId Propagation

Every event carries a correlationId that links the originating HTTP request to all downstream processing — including synchronous cross-service HTTP calls (ACL validation) and asynchronous SQS event handlers. This enables end-to-end request tracing across all service boundaries without depending on X-Ray.

How It Works

  1. HTTP request — correlationMiddleware() generates a UUID and stores it in AsyncLocalStorage. If x-correlation-id header is present, it reuses that value instead.
  2. Logger — createLogger() automatically reads the correlationId from AsyncLocalStorage and includes it in every log line.
  3. ACL adapter (cross-service HTTP call) — getCorrelationHeaders() returns { 'x-correlation-id': id } which is spread into outbound request headers. The receiving service's correlationMiddleware() reuses the incoming header, so all logs on both sides share the same correlationId.
  4. SQS publisher — SqsStandardEventPublisher / SqsFifoEventPublisher calls getCorrelationId() and merges it into the event body before JSON.stringify. No manual code needed.
  5. Event handler — extracts correlationId from the raw message body (before Zod parsing), then wraps processRecord() in runWithCorrelationId(). All log lines inside the handler carry the same correlationId as the original HTTP request.

Event Schema Requirement

All event schemas must include correlationId: z.string().optional() so the auto-injected field passes Zod validation on the consumer side. The field is optional because events published outside of an HTTP request context (e.g. from a migration script) won't have one.

Adding a New Event Type

  1. Domain constants — add the event type to the domain's event type enum (e.g., UserEventTypeEnum).
  2. Event schema — add a Zod schema in contracts/src/{domain}/event-schemas.ts and include it in the discriminated union.
  3. Handler class — create handlers/{event-name}.handler.ts implementing IEventHandler<T>.
  4. Wire — inject the handler into the event handler service constructor, add the case to the switch, register in the module.
  5. Publisher — in the API service's use case, call publisher.publish({ eventType, ... }).

Adding a New Event Handler Service

  1. Create the folder structure under apps/{domain}/{domain}-event-handler-service/.
  2. Create main.ts with the dual-mode pattern (local polling + Lambda handler).
  3. Create NormalizedSqsRecord and IEventHandler interfaces.
  4. Create the event handler application service with Zod parse + switch dispatch.
  5. Create SqsLocalService for local polling.
  6. Wire everything in the domain module — no controllers array.
  7. Add the SQS queue to scripts/setup-localstack.ts.
  8. Add env vars: {DOMAIN}_SQS_QUEUE_URL, {DOMAIN}_SQS_QUEUE_NAME.
  9. Add VS Code task: Service: Serve {domain}-event-handler-service.
