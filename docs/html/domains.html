Bounded Contexts & Domain Model

Three core bounded contexts — User, Product, and Order — each with their own entity, state machine, persistence, and business rules. Two supporting services — Auth and Files — provide cross-cutting infrastructure to all domains without owning business data. Each domain owns its data completely and communicates with others through well-defined interfaces.

Strategic Domain Classification

Domain-Driven Design distinguishes between Core, Supporting, and Generic subdomains. This classification drives where the team invests the most modeling effort, where simpler patterns suffice, and how each domain justifies its complexity budget.

Domain Classification Rationale
Order Core Domain The primary source of business value. Orchestrates the most complex workflows — aggregate root with child entities (OrderItem, OrderPayment), choreography saga for async product validation, ACL integration with the User domain, and the richest state machine (DRAFT → PENDING → CONFIRMED → SHIPPED → DELIVERED, plus CANCELLED and VALIDATION_FAILED branches).
Product Supporting Subdomain Enables the core domain to function. Product catalog, pricing, and lifecycle events feed directly into order creation and validation. Publishes the most event types (6 events). Non-trivial business rules (status lifecycle, price change tracking), but does not own the primary business workflow.
User Supporting Subdomain Provides identity and access management — required by the core domain (customer validation via ACL) but contains standard CRUD + status lifecycle logic. Simplest entity model (single entity, no children). Could potentially be replaced by an external identity provider with minimal impact on the core.

How Classification Appears in This Codebase

Design Decision Core (Order) Supporting (Product, User)
Entity complexity Aggregate root with OrderItem[] and OrderPayment children. Factory methods manage the full object graph. Flat single entity. No child entities or aggregates.
State machine depth 7 statuses with branching paths (DRAFT → PENDING/VALIDATION_FAILED, PENDING → CONFIRMED → SHIPPED → DELIVERED, any → CANCELLED). Guarded transitions with domain exceptions. 4–5 statuses with linear progressions (PENDING → ACTIVE → INACTIVE → DELETED). Straightforward guards.
Cross-domain integration Consumes events from Product (price changes, discontinuation). Uses ACL to validate customers via User API. Publishes saga-initiating events. Product publishes lifecycle events. User is fully independent (no outbound dependencies).
Persistence Prisma + PostgreSQL — relational model for aggregate with joins, transactions, and cascade deletes. DynamoDB OneTable — single-table design optimized for key-value lookups and status-based listing.
Saga participation Initiator (publishes ORDER_CREATED) and resolver (handles validation result). Owns the provisional state (DRAFT) until the saga completes. Product is the saga responder (validates products, publishes result). User does not participate in sagas.
Why does this matter? The core domain is where competitive advantage lives — invest the deepest modeling, richest testing, and most careful invariant enforcement here. Supporting subdomains should be good enough without over-engineering. Generic subdomains (not implemented in this template) should ideally be replaced by off-the-shelf solutions.

DDD Concepts as They Appear in Code

This template applies Domain-Driven Design pragmatically. Here's how each DDD concept maps to the codebase:

DDD Concept In This Codebase Example
Bounded Context Each packages/{domain}-domain is a bounded context with its own entity, constants, exceptions, and repository interface. No domain imports from another domain package. packages/order-domain owns everything about orders — statuses, items, payments, validation rules.
Entity A class with a private constructor, create() factory (new instances), reconstitute() factory (from DB), getters, and business methods that enforce invariants. User.create({ email, firstName, lastName }) validates email format and sets status to PENDING.
Aggregate Root An entity that owns child entities. Only the root is accessed via the repository. Children are created/managed through the root. Order is the aggregate root for OrderItem[] and OrderPayment.
Repository Interface An abstract class in application/interfaces/ that declares persistence operations. The domain defines what; infrastructure provides how. IOrderRepository.save(order), IOrderRepository.findById(orderId)
Use Case A single-responsibility class in application/use-cases/ with an execute() method. Each operation (create, activate, cancel…) is its own use case. CreateOrderUseCase.execute(input) validates customer via ACL, creates entity, saves, publishes event.
Domain Exception Typed error classes in domain/exceptions/. Each represents a specific business rule violation. Mapped to HTTP status codes by DomainExceptionFilter. CannotCancelOrderError → 409, OrderNotFoundError → 404
Anti-Corruption Layer (ACL) An abstract class in application/interfaces/ defining what the domain needs from another bounded context, without importing upstream types. Infrastructure provides an HTTP adapter. ICustomerValidator.validate(customerId) — order domain's interface. UserApiClient — the HTTP adapter.
Published Language Event schemas in @old-st/contracts/{domain}/event-schemas.ts. This is the shared vocabulary between publisher and consumer domains. productDomainEventSchema — Zod discriminated union of all product event types.
Domain Event A JSON message published to SQS with a type discriminator and typed payload. Constants in domain/constants/, schemas in contracts/. { type: 'ORDER_CREATED', orderId, customerId, items }

Solid arrows = valid transitions · Dashed arrows = blocked (throws error)

Business Rules

  • New users are created with status PENDING, emailVerified: false, and default role USER.
  • Email must match a valid format — enforced in create().
  • activate() requires PENDING status and emailVerified === true. Both guards must pass.
  • deactivate() is blocked for DELETED users and already INACTIVE users.
  • markAsDeleted() is a soft delete — transitions any non-deleted status to DELETED.
  • Profile updates (updateProfile, updateData) and role changes (changeRole) are blocked for DELETED users.
  • changeRole() throws if the user already has the target role.

Business Rules

  • New products are created with status ACTIVE.
  • activate() only works from INACTIVE.
  • deactivate() only works from ACTIVE.
  • discontinue() works from ACTIVE or INACTIVE — it's a one-way transition.
  • Updates to details, price, and inventory are blocked for DELETED and DISCONTINUED products.
  • Price must be > 0, inventory must be >= 0, name cannot be empty.

Aggregate Structure

Order is an aggregate root that owns two child entities:

flowchart TD subgraph Order["Order (Aggregate Root)"] O1["orderId: string"] O2["customerId: string"] O3["orderStatus: OrderStatus"] O4["totalAmount: number"] O5["create() · addItem() · removeItem() confirmOrder() · cancel() · refund() approveProductValidation() · failValidation()"] end subgraph OrderItem["OrderItem (0..* per Order)"] I1["itemId · productId · productName"] I2["quantity · unitPrice · latestKnownPrice"] I3["updateQuantity() · updateLatestKnownPrice() hasPriceDrift() · getSubtotal()"] end subgraph OrderPayment["OrderPayment (0..1 per Order)"] P1["paymentId · method · amount · status"] P2["markSuccessful() · fail() · refund()"] end Order -->|"owns 0..*"| OrderItem Order -->|"owns 0..1"| OrderPayment style Order fill:#dcfce7,stroke:#16a34a style OrderItem fill:#dbeafe,stroke:#2563eb style OrderPayment fill:#fef3c7,stroke:#d97706

Business Rules

  • New orders start in DRAFT — items can be added/removed/updated only while in DRAFT.
  • The choreography saga resolves DRAFT orders: approveProductValidation() transitions to PENDING, failValidation() transitions to VALIDATION_FAILED.
  • confirmOrder() requires PENDING status, at least one item, a payment, and no price drift on any item.
  • Price drift guard: if any OrderItem.latestKnownPrice differs from unitPrice, confirmOrder() throws PriceDriftDetectedError.
  • cancel() is available from most statuses except DELIVERED, REFUNDED, and VALIDATION_FAILED.
  • refund() requires DELIVERED status with a successful payment.
  • totalAmount is automatically recalculated when items are added, removed, or updated.

Import rule Cross-domain services import from @old-st/contracts/{domain} (published language) — never from @old-st/{domain}-domain (internal domain package). This prevents tight coupling between bounded contexts.

Entity Pattern Summary

Every entity in this template follows the same structural pattern:

export class EntityName {
  // 1. Private constructor — entities cannot be instantiated with `new`
  private constructor(
    private readonly id: string | null,
    private field: Type,
    // ...
  ) {}

  // 2. create() factory — for new instances (not yet persisted)
  //    Validates invariants, sets defaults (status, timestamps)
  static create(props: { ... }): EntityName { }

  // 3. reconstitute() factory — for hydrating from database
  //    No validation — trusts persisted data
  static reconstitute(props: { ... }): EntityName { }

  // 4. Business methods — enforce state transitions and invariants
  //    Throw typed domain exceptions on rule violations
  activate(): void { }
  deactivate(): void { }
  cancel(): void { }

  // 5. State query helpers
  isActive(): boolean { }
  isDeleted(): boolean { }

  // 6. Getters — encapsulated access, no public fields
  getId(): string | null { }
  getStatus(): Status { }
}
