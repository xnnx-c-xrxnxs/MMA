Clean Architecture

How the layers are organized, what each layer owns, and the rules that keep boundaries clean across every service.

Layer Hierarchy

Every service in this monorepo follows the same four-layer architecture. Dependencies flow inward only — outer layers depend on inner layers, never the reverse.

Layer Responsibilities

Layer Owns Must NOT Location
Presentation HTTP routing, Zod validation (pipes), error-to-HTTP mapping (filters), Swagger decorators Call use cases directly, contain business logic, return domain entities apps/{domain}/{service}/src/presentation/
Application Orchestration across use cases, entity → DTO mapping via schema.parse(), event publishing coordination Contain business rules, access the database, know about HTTP or NestJS decorators apps/{domain}/{service}/src/application/
Domain (Use Cases) Single-purpose operations — one use case per action (create, activate, cancel…) Know about HTTP, DTOs, contracts, or specific DB technology packages/{domain}-domain/src/application/use-cases/
Domain (Entities) Business rules, invariants, state transitions, validation guards Import NestJS, contracts, infrastructure, or any framework code packages/{domain}-domain/src/domain/entities/
Infrastructure Repository implementations, DB schemas, ACL HTTP adapters, config Add business logic, expose domain entities to the outside, decide business outcomes packages/{domain}-domain/src/infrastructure/
The dependency rule Inner layers define interfaces (e.g., IOrderRepository). Outer layers provide implementations (e.g., PrismaOrderRepository). This is dependency inversion — the domain dictates the contract, infrastructure fulfills it.

Key observations from this flow

  • Controller → Application Service → Use Case — the controller never calls the use case directly.
  • Zod validation happens first — invalid input is rejected before hitting any business logic.
  • The ACL call is transparent to the use case — it calls ICustomerValidator.validate(), unaware that an HTTP call is happening under the hood.
  • The entity enforces invariants — Order.create() throws CustomerIdRequiredError if the customerId is empty.
  • The repository interface is the boundary — the use case calls save() on IOrderRepository, unaware of Prisma or PostgreSQL.
  • DTO mapping uses Zod — the application service calls schema.parse() to transform the entity into a type-safe DTO. No toObject() methods on entities.
  • Event publishing happens in the use case — ORDER_CREATED is published as part of the domain operation, keeping it self-contained.

Golden Rules

These rules are enforced across every service. They exist to prevent architectural drift as the codebase grows.

Layer Boundaries

  1. Controllers never call use cases directly. Application Services always sit between the controller and the domain.
  2. Application Services are always present — even for simple pass-through operations. This keeps the architecture consistent and provides a stable DTO mapping point.
  3. Use Cases return domain entities. The Application Service transforms them to DTOs.
  4. Application Services transform entities to DTOs using Zod schema.parse() from the contracts package.
  5. Domain layer has zero dependencies on contracts or NestJS. Entities are pure TypeScript classes.

Domain Purity

  1. Infrastructure implements repository interfaces and does not add business logic.
  2. Zod validation lives in the presentation layer (pipes, DTO parsing) and the contracts package.
  3. Domain constants are the single source of truth — UserStatusEnum, ProductStatusEnum, OrderStatusEnum. Never hardcode string literals like 'PENDING' or 'ACTIVE'.
  4. Entity timestamps are dateCreated + updatedAt only. Never add a createdAt field to entities.
  5. Never add toObject() to entities. Serialization is handled by the Application Service → Zod parse pipeline.

Error Handling

  1. Typed domain exceptions map to HTTP errors via DomainExceptionFilter. Domain errors → 404/409, application errors → 400, unexpected → 500.
  2. Never trust userId from client input. Authentication context determines the current user.

Cross-Domain

  1. Never import from the bare @mma/contracts root. Always use domain-scoped subpath imports: @mma/contracts/user, @mma/contracts/order, etc.
  2. Synchronous cross-service calls must use an ACL. The consuming domain defines an abstract validator interface; the infrastructure layer provides the HTTP adapter.
  3. Cross-domain event consumers import from the publishing domain's contracts only — never from its domain package.

Persistence

  1. Prisma domains use offset pagination; DynamoDB domains use cursor pagination. Never mix within a domain.
  2. Prisma schema enums must mirror domain constants exactly. The domain constants are the single source of truth.
  3. The Prisma client is infrastructure-only. Domain and application layers never import from @prisma/client.

Where Code Lives

Every domain follows the same split between the domain package (business logic, framework-free) and the service app (NestJS, HTTP/SQS handling):

Domain Package

packages/{domain}-domain/src/
  domain/
    entities/          ← Entity class (business rules + invariants)
    constants/         ← Status enums, event types
    exceptions/        ← Domain errors (map to 404/409)
  application/
    use-cases/         ← One class per operation
    interfaces/        ← Repository interface, ACL validators
    exceptions/        ← Application errors (map to 400)
  infrastructure/
    schemas/           ← DynamoDB OneTable schema (DynamoDB domains)
    prisma/            ← Prisma schema + migrations (Prisma domains)
    repositories/      ← Repository implementation

Service App (HTTP API)

apps/{domain}/{service}/src/
  presentation/
    controllers/       ← NestJS controllers (routes + Swagger)
    pipes/             ← ZodValidationPipe
    filters/           ← DomainExceptionFilter
  application/
    services/          ← Application Service (orchestration + DTO mapping)
  infrastructure/
    config/            ← DynamoDBConfig or PrismaConfig
    clients/           ← ACL HTTP adapters (optional)
  modules/
    {domain}.module.ts ← NestJS module wiring

Service App (SQS Consumer)

apps/{domain}/{service}/src/
  application/
    interfaces/        ← NormalizedSqsRecord
    services/          ← Event handler service (switch dispatch)
      handlers/        ← Per-event handler classes
  infrastructure/
    config/            ← DynamoDBConfig or PrismaConfig
    sqs/               ← SqsLocalService (local polling)
  modules/
    {domain}.module.ts ← NestJS module wiring (no controllers)
