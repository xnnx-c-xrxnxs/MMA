Deployment & CD Pipeline

How the GitHub Actions CD pipeline works — from bootstrap to first deployment, preview environments, and the data-driven Terraform pattern that makes most service additions require zero infrastructure file edits.

Deployment Model

Backend services deploy as Lambda ZIP packages connected to a shared API Gateway HTTP API v2 per environment. AWS Lambda Web Adapter proxies invocation events to a plain NestJS HTTP server inside the Lambda — no @codegenie/serverless-express or dual-mode handler export.

The webapp deploys as a static Next.js export (output: 'export') to S3 + CloudFront — no Docker container or server process required. CloudFront serves pre-built HTML/CSS/JS with SPA routing (403/404 → /index.html). The mode is configured in service-registry.json → webapp.deploymentMode (defaults to "static" for all environments). All infrastructure is described in Terraform and driven by .github/service-registry.json.

Data-Driven Infrastructure

.github/service-registry.json is the single source of truth for both CI and CD. All Terraform environment roots read this file via jsondecode(file(...)) and create resources with for_each.

Change Terraform edits needed
Add a new API service None — add entry to apiServices[]
Add a new event-handler service None — add entry to eventHandlerServices[]
Add a DynamoDB table None — add to infrastructure.dynamodbTables[]
Add an SQS queue None — add to infrastructure.sqsQueues[]
Add an S3 bucket None — add to infrastructure.s3Buckets[]
Add an RDS PostgreSQL database None — add to infrastructure.rds[]
Change memory, timeout, env vars None — update the service entry
Introduce a new AWS service type (e.g., ElastiCache) Requires a new Terraform module

CD Workflows

Workflow Trigger Purpose
cd-deploy.yml Push to develop→dev, main→staging, or manual Build affected services → Terraform apply → run deploy tasks (migrations/seeds) → deploy Lambdas + webapp → smoke test
cd-infra-plan.yml PR with infra/** or service-registry.json changes Terraform plan for dev/staging/prod — posts plan as PR comment
cd-preview-create.yml Manual dispatch Create or update a full-stack preview environment
cd-preview-destroy.yml Manual dispatch Tear down a preview environment
cd-destroy.yml Manual dispatch (double-confirm) Permanently destroy an entire dev/staging/prod environment

CD Deploy Pipeline Jobs

Build Lambda ZIPs\n(affected services)"] init["5. Run init tasks\n(migrations, seeds)"] deploy["6. Deploy\n(upload ZIPs + push webapp)"] smoke["7. Smoke test\n(GET /health on all services)"] preflight --> detect --> tf --> build --> init --> deploy --> smoke
  1. Preflight — validates required GitHub variables are set.
  2. Detect changes — uses Nx to find affected services (skipped if deploy_all=true).
  3. Terraform apply — creates/updates all AWS resources from service-registry.json.
  4. Build Lambda ZIPs — packages affected services into ZIP artifacts.
  5. Run init tasks — ECS init-runner applies Prisma migrations and runs seed scripts from within the VPC.
  6. Deploy — uploads Lambda ZIPs to S3 + updates function code, builds/pushes webapp Docker image.
  7. Smoke test — hits GET {base-url}/health on every service. Posts results to GitHub Step Summary.

Bootstrap (One-Time Setup)

Before first deployment, run infra/bootstrap/ to create the infrastructure the CD pipeline itself needs: S3 state bucket, DynamoDB lock table, ECR repository, GitHub OIDC provider, and IAM deploy role.

See docs/deployment.md for the complete step-by-step bootstrap guide.

GitHub OIDC — No Secrets in CI

GitHub Actions authenticates to AWS via OIDC — no AWS credentials are ever stored as GitHub secrets. The bootstrap module creates:

  • An OIDC identity provider in AWS IAM
  • An IAM deploy role with a trust policy allowing GitHub Actions to assume it

Workflows use aws-actions/configure-aws-credentials@v4 with role-to-assume.

DEPLOY_ENABLED Sentinel

Push-triggered deployments are blocked by default until you set DEPLOY_ENABLED=true as an environment-scoped GitHub variable for each target environment (dev/staging/prod).

Set in: GitHub → Settings → Environments → {env} → Variables → DEPLOY_ENABLED=true

Manual dispatch always runs regardless of DEPLOY_ENABLED. This flag only gates push-triggered (automatic) deployments.

Secrets Management (SENSITIVE_VARS)

Sensitive values (database passwords, external API keys) flow through the pipeline as a JSON blob via the SENSITIVE_VARS GitHub secret:

  1. Create infra/bootstrap/github-secrets (gitignored) with your values: 
    SOME_API_KEY=value
ANOTHER_SECRET=value
  2. The AWS: Bootstrap Apply task reads this file and creates the SENSITIVE_VARS secret in GitHub.
  3. CD workflows pass SENSITIVE_VARS to Terraform, which writes selected keys to AWS Secrets Manager.
  4. Lambda services read their secrets at cold-start via SecretsConfig.resolve(allowList).
RDS passwords are auto-generated. Terraform uses a random_password resource — you don't need to put database passwords in github-secrets. Only pre-existing external credentials go there.

Smoke Test

After every deployment, the CD pipeline sends GET {base-url}/health to every registered API service. Results are posted to the GitHub Step Summary.

Every API service must expose GET /health. The route must use @Get('health') (not @Get()), be decorated with @Public(), and return { status: 'ok', service: '{service-name}' }. A service that fails the health check will mark the deployment as failed.

ECS Init-Runner (Deploy Tasks)

RDS instances are inside a private VPC — the CI runner has no network path to them. Prisma migrations and other post-deploy scripts are executed via the ECS init-runner: a one-shot Fargate container defined in infra/init-runner/.

The deployTasks array in service-registry.json declares what the init-runner must run: 

{
  "deployTasks": [
    {
      "name": "orders-migrations",
      "type": "prisma-migrate",
      "domain": "order",
      "requiresVpc": true,
      "secretEnvVars": ["ORDERS_DATABASE_URL"],
      "envVars": ["AWS_SECRETS_ARN"]
    }
  ]
}

When deployTasks is empty, zero ECS resources are created and the CD workflow skips the init-runner job entirely — zero cost.
