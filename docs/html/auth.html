Authentication

How authentication works end-to-end — from the auth-api-service through the JWT auth guard on every API service to the AuthProvider on the frontend. Covers both local development (no Cognito) and deployed environments (AWS Cognito).

Architecture Overview

graph LR Client["Browser / Mobile"] AuthSvc["auth-api-service\nport 3003"] ApiSvc["user / product / order\nAPI services"] IAuth["IAuthProvider\n<abstract>"] Cognito["CognitoAuthProvider\n(deployed)"] Local["LocalAuthProvider\n(STAGE=local)"] Guard["JwtAuthGuard\n(per service)"] Client -->|POST /auth/sign-in| AuthSvc AuthSvc --> IAuth IAuth --> Cognito IAuth --> Local Client -->|Bearer token| ApiSvc ApiSvc --> Guard

The auth-api-service is the single auth boundary. It delegates to an IAuthProvider abstraction — CognitoAuthProvider in deployed environments and LocalAuthProvider locally (STAGE=local). No other service talks to Cognito directly.

Every other API service (user-api-service, order-api-service, etc.) has its own copy of JwtAuthGuard that verifies the JWT on each request. The guard is provider-agnostic — it reads env vars, not Cognito SDK calls.

Local Development

When STAGE=local, the LocalAuthProvider is used. No Cognito setup is required. The local provider accepts a single hardcoded credential:

FieldValue
Emailadmin@test.com
PasswordPassword123!

The local provider issues unsigned JWT tokens. The JwtAuthGuard on all services bypasses JWKS verification when STAGE=local — it decodes the token payload without signature verification.

The refresh token format locally is: local-refresh-{userId}-{timestamp} (stateless — no database lookup needed).

No Cognito needed locally. Start auth-api-service with STAGE=local and sign in immediately with the credentials above. All other services will accept the unsigned tokens automatically.

Auth API Endpoints

Method Path Auth Required Description
POST /auth/sign-in ❌ Sign in with email + password. Returns access + id tokens. Sets httpOnly refresh cookie.
POST /auth/new-password ❌ Set new password after first sign-in challenge (Cognito NEW_PASSWORD_REQUIRED flow).
POST /auth/refresh-session ❌ (cookie) Silent token refresh. Reads the httpOnly refresh cookie. Returns new access + id tokens.
POST /auth/forgot-password ❌ Send a password reset code to the user's email.
POST /auth/confirm-forgot-password ❌ Confirm password reset with code + new password.
POST /auth/change-password ✅ Change password (authenticated user).
POST /auth/sign-out ✅ Sign out. Revokes tokens, clears the httpOnly cookie.
GET /auth/me ✅ Get current user details from Cognito (or local mock).
GET /health ❌ Health check — returns { status: 'ok', service: 'auth-api-service' }.

httpOnly Cookie — Critical Details

Refresh tokens are stored as httpOnly cookies. The cookie parameters differ by environment:

Parameter Local (STAGE=local) Deployed
httpOnly true true
secure false true
sameSite Lax None
path / /
maxAge 30 days 30 days
Why SameSite=None in deployed mode? The frontend (ALB, e.g. app.example.com) and the API Gateway (api.execute-api.eu-west-2.amazonaws.com) are on different origins. SameSite=None with Secure=true is the only combination that allows cross-origin cookie sending. Never use SameSite=Strict in deployed mode — the browser will not send the cookie on cross-origin requests.

JWT Auth Guard (Per-Service)

Every HTTP API service has its own copy of JwtAuthGuard in presentation/guards/jwt-auth.guard.ts. The guard is not a shared package — each service owns its copy.

The guard reads three environment variables:

Env VarPurpose
JWT_JWKS_URI JWKS endpoint for token verification (e.g., Cognito JWKS URL). Ignored locally.
JWT_ISSUER Expected iss claim. Tokens with wrong issuer are rejected. Ignored locally.
JWT_USER_ID_CLAIM Name of the claim holding the user ID (default: sub). Configurable for Auth0 / Keycloak.

This design makes the guard provider-agnostic: it works with AWS Cognito, Auth0, Keycloak, or any OIDC-compatible provider without code changes.

Use the @Public() decorator to exempt an endpoint from auth: 

@Get('health')
@Public()
health() {
  return { status: 'ok', service: 'user-api-service' };
}

Two-Tier Auth: API Gateway + NestJS

In every deployed environment, an inbound API request is authenticated twice — once at the API Gateway edge (using a JWT authorizer wired to the Cognito User Pool's JWKS), and once inside the Lambda by NestJS's JwtAuthGuard. Both must pass.

TierWhere it runsWhat it validatesReject behavior
Edge (gateway) API Gateway HTTP API v2 JWT authorizer Token signature (JWKS), iss, aud, exp 401 returned before Lambda is invoked — no cold start, no log entry
NestJS JwtAuthGuard (per-service) Same as above + populates request.user for @CurrentUser() 401 from inside Lambda (you'll see the request log)

Why two tiers? The gateway-side check is a hard perimeter: invalid traffic never reaches Lambda, so there's no cold-start cost and no DDoS amplification. The NestJS guard is what populates request.user, so application code can use @CurrentUser() without re-parsing the token.

Public Routes

Endpoints that must be reachable without a token (sign-in, password reset, /health, /swagger) are declared in two places, and the two MUST agree:

  1. The controller method has @Public() — bypasses the NestJS guard.
  2. The path is listed in .github/service-registry.json → gatewayAuth.publicRoutes for that service — bypasses the gateway authorizer.

Drift is detected by the gateway-public-routes-sync structural lint check (run by pnpm lint:standards). If the counts don't match, CI fails before the PR can merge. See the gateway-jwt-auth skill for the full registry schema and Terraform wiring.

Standard public routes for every new HTTP API service

When you scaffold a new service, the registry must include:

{ "service": "{name}", "method": "GET", "path": "/api/health" },
{ "service": "{name}", "method": "GET", "path": "/api/swagger" },
{ "service": "{name}", "method": "GET", "path": "/api/swagger-json" }

/api/health is required because the CD smoke test hits it after deployment and only accepts 200. /api/swagger* are listed even though Swagger itself is gated by SWAGGER_ENABLED=true — the gateway has no way to know whether the service serves the route, and unused gateway routes return harmless 404s rather than confusing 401s.

Reading the Authenticated Actor — @CurrentUser()

Every API service ships a per-service param decorator at presentation/decorators/current-user.decorator.ts alongside an express.d.ts type augmentation. The decorator extracts the AuthenticatedUser = { userId, email, userRole? } object that JwtAuthGuard populates on request.user after JWT verification.

Golden Rule #45 — controllers MUST read the actor identity via @CurrentUser(). Never accept userId, actorId, performedBy, or requesterId from @Body() or @Query() — that is the canonical broken-access-control vulnerability. Path params like :userId are allowed when they identify the subject of an admin action; the actor still comes from the JWT. 

@Post()
async createOrder(
  @CurrentUser() user: AuthenticatedUser,
  @Body(new ZodValidationPipe(createOrderSchema)) body: CreateOrderInput,
) {
  return this.orderService.create({ ...body, customerId: user.userId });
}

// Single-field extraction:
@Get('me')
async me(@CurrentUser('userId') userId: string) { /* ... */ }

Enforced by the no-userId-in-controller-input structural lint check in scripts/lint-standards.ts (run by ci-fast-check.yml). See the current-user-decorator skill for full patterns.

Cross-Service Actor Propagation

When an API service calls another bounded context synchronously (Pattern 1 — Sync ACL), the outbound HTTP request must carry BOTH the originating Authorization header and the x-correlation-id. This is handled by getOutboundHeaders() from @mma/telemetry: 

import { getOutboundHeaders } from '@mma/telemetry';

await fetch(url, {
  headers: {
    'Content-Type': 'application/json',
    ...getOutboundHeaders(),   // forwards Authorization + x-correlation-id
  },
});

correlationMiddleware() captures both values from the inbound request and stores them in AsyncLocalStorage; getOutboundHeaders() reads them back. The downstream service's @CurrentUser() resolves to the same actor end-to-end, and the trace chain stays intact across the entire call graph.

Golden Rule #46. The legacy getCorrelationHeaders() sends only the correlationId and is kept for backward compatibility — prefer getOutboundHeaders() for any cross-service call to an authenticated endpoint.

Frontend — AuthProvider

The AuthProvider in packages/client-common handles the client-side auth lifecycle:

  • Silent refresh on mount — calls POST /auth/refresh-session with credentials: 'include' to restore the session from the httpOnly cookie. This runs on every page load.
  • Access token memory-only — stored in React state, never in localStorage or sessionStorage. Lost on page refresh; restored via silent refresh.
  • 401 auto-retry — when any API call returns 401, the base API client calls refresh once and retries. If refresh fails, the user is redirected to login.
  • Re-entrancy guard — multiple concurrent 401s trigger only one refresh call.

CORS Configuration

Every API service enables CORS with credentials:

// main.ts (every API service)
app.enableCors({
  origin: process.env.FE_BASE_URL,
  credentials: true,
});
Never use origin: '*' with credentials: true. The W3C spec forbids it — browsers reject it. Always use a specific origin.

Contracts

Auth schemas live in @mma/contracts/auth (packages/contracts/auth/src/schemas.ts):

  • signInSchema / SignInInput
  • signInResponseSchema / SignInResponse (discriminated union: SUCCESS | NEW_PASSWORD_REQUIRED)
  • refreshSessionResponseSchema / RefreshSessionResponse
  • forgotPasswordSchema / ForgotPasswordInput
  • confirmForgotPasswordSchema / ConfirmForgotPasswordInput
  • changePasswordSchema / ChangePasswordInput
  • meResponseSchema / MeResponse
