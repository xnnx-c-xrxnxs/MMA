Four Communication Patterns

The template demonstrates four distinct inter-service patterns. Each has specific rules about when to use it and how to implement it.

Pattern 1 — Synchronous ACL Call Sync

When: A use case needs a real-time yes/no answer from another service before proceeding (gate check). The operation cannot proceed without the answer.

Example: Order API validates that the customer exists and is ACTIVE by calling User API before creating or confirming an order.

Architecture

ComponentLocationResponsibility
Port (abstract class) packages/order-domain/src/application/interfaces/customer-validator.interface.ts Defines what the order domain needs: validate(customerId): Promise<ValidatedCustomer>
Adapter (HTTP client) apps/orders/order-api-service/src/infrastructure/clients/user-api.client.ts Implements the port using HTTP. Maps HTTP errors to domain exceptions. 5-second timeout.
Wiring NestJS module: HttpModule import + useClass provider for ICustomerValidator Injects the adapter wherever the port is needed.

Key Rules

  • The consuming domain defines its own interface and response type — it never imports from the upstream domain package.
  • The use case receives ICustomerValidator via constructor injection alongside the repository.
  • HTTP error mapping (404 → domain not found, 409 → invalid state, 5xx → service unavailable) happens in the adapter, not the use case.
  • Always set a timeout on cross-service calls (5 seconds in this template).
  • Uses API_USER_URL from .env.local.

Pattern 2 — Cross-Domain Async Events Async

When: One domain needs to react to lifecycle events from another domain, with eventual consistency being acceptable. The publishing domain doesn't wait for the consumer's response.

Example: Product API publishes PRODUCT_PRICE_CHANGED → Order Event Handler updates latestKnownPrice on draft order items containing that product.

Key Rules

  • The consumer imports event schemas from @mma/contracts/product only — never from @mma/product-domain.
  • Handlers write to the consuming domain's own repository — never to the publishing domain's data.
  • Fire-and-forget: the publisher returns immediately after queuing the message.

Pattern 3 — Intra-Domain Events Async

When: A service within the same bounded context reacts to its own domain events. Both publisher and consumer share the same domain package.

Example: User API publishes USER_DELETED → User Event Handler archives the user data (e.g., to S3 for compliance).

Key Difference from Cross-Domain

  • Both publisher and consumer import from @mma/contracts/user and @mma/user-domain — no ACL boundary needed since they're in the same bounded context.

Pattern 4 — Choreography Saga Saga

When: An operation requires asynchronous coordination between two bounded contexts with a request → response cycle and eventual state resolution. The operation cannot succeed without the other domain's answer, but the answer arrives asynchronously.

Example: Order creation triggers product validation. The order starts in DRAFT and waits for the product domain to confirm that all items are valid before moving to PENDING.

Saga Participants

RoleServiceWhat It Does
Initiator order-api-service Creates order in DRAFT, publishes ORDER_CREATED to product-events queue
Responder product-event-handler-service Validates all products (exist, active, price match), publishes result to order-events queue
Resolver order-event-handler-service Receives validation result, transitions order: DRAFT → PENDING or DRAFT → VALIDATION_FAILED

Saga Rules

  • Provisional state: The initiating domain starts in DRAFT — not the final state. The client sees DRAFT immediately.
  • Result event, not command: The responding domain publishes a result (SUCCEEDED/FAILED), not a command. The consuming domain decides how to interpret it.
  • Idempotent handlers: The resolver checks the order status before transitioning. If the order has already moved out of DRAFT (e.g., duplicate message delivery), the handler catches the typed domain exception (CannotApproveProductValidationError / CannotFailValidationError) and skips — it does not rethrow.
  • Each participant writes to its own repository only. The product handler reads products from the product repo. The order handler writes to the order repo. No cross-writing.
  • Event publishing happens in the use case, not the application service — keeps the use case self-contained.

What Happens to the Order Item Prices?

The saga validates that product prices at order creation match the current catalog prices. After validation succeeds, the order moves to PENDING. But prices can still change before the customer confirms — that's where the price drift guard comes in:

  1. Cross-domain PRODUCT_PRICE_CHANGED events update latestKnownPrice on draft order items.
  2. When the customer calls confirmOrder(), the entity checks if latestKnownPrice !== unitPrice for any item.
  3. If drift is detected, PriceDriftDetectedError is thrown — the customer must re-create the order.
