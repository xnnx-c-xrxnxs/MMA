Module 1

Why Clean Architecture?

The problem with writing code without architectural discipline — and why it matters at scale.

The Problem It Solves

Without architectural discipline, codebases naturally drift toward the “Big Ball of Mud” — where everything knows about everything, changing one thing breaks three others, and testing requires booting the entire application.

❌ Without Clean Architecture
  • Controllers query the database directly
  • Business rules scattered across HTTP handlers
  • Can't test without a real database
  • Switching from DynamoDB to Postgres = rewrite
  • Domain logic leaks into framework code
  • Every change risks breaking unrelated features
vs
✅ With Clean Architecture
  • Business rules know nothing about HTTP or databases
  • Domain logic is pure TypeScript — unit-testable
  • Swap DynamoDB for Postgres without touching use cases
  • Add a new API without changing business rules
  • New developers can read domain code without NestJS knowledge
  • Frameworks are tools, not constraints

The Core Promise

“The architecture should scream what the application does, not what framework it uses.” — Robert C. Martin (Uncle Bob)

When you open packages/user-domain/ you should immediately understand it's about users — not about NestJS, DynamoDB, or HTTP. The frameworks are implementation details pushed to the outer edges.

🔧 Independent of Frameworks

Domain and application layers have zero NestJS imports. You could run them in a CLI, a Lambda, or a different web framework without changing a line.

🧪 Testable by Design

Business rules are tested with plain unit tests — no database, no HTTP server, no mocking of framework internals. Just mock the repository interface.

🔀 Database Independent

The domain defines what data is needed via repository interfaces. The infrastructure decides how it's stored. Swap DynamoDB for Prisma without touching use cases.

🌐 UI Independent

The same use cases power the REST API, the Next.js webapp, and the Expo mobile app. Business logic is written once and consumed by any client.

Module 3

The Dependency Rule

The single rule that drives everything else: source code dependencies can only point inward.

The One Rule to Remember

“Source code dependencies can only point inwards. Nothing in an inner circle can know anything about something in an outer circle.” — Uncle Bob

In practice this means:

  • The Domain layer imports from nobody (it is the innermost circle).
  • The Application layer imports only from Domain.
  • The Infrastructure (repository implementation) imports from Application and Domain.
  • The Presentation (controllers) imports from Application (via Application Service).

How the Repository Interface Solves the Problem

The Domain needs data persistence, but it cannot import from the Infrastructure (that would violate the rule). The solution is Dependency Inversion:

  1. The Application layer defines an abstract repository interface (IUserRepository).
  2. The Infrastructure layer implements that interface (DynamoUserRepository implements IUserRepository).
  3. The NestJS Module wires the concrete implementation to the abstract token at startup.
  4. Use cases only ever see the interface — never the DynamoDB/Prisma implementation.
// Application layer — defines the contract (interface)
// packages/user-domain/src/application/interfaces/user-repository.interface.ts
export abstract class IUserRepository {
  abstract save(user: User): Promise<User>;
  abstract findById(userId: string): Promise<User | null>;
  abstract findByEmail(email: string): Promise<User | null>;
}

// Use case only knows IUserRepository — no DynamoDB, no Prisma
export class CreateUserUseCase {
  constructor(private readonly userRepository: IUserRepository) {}
  // ...
}

// Infrastructure layer — provides the concrete implementation
// packages/user-domain/src/infrastructure/repositories/dynamo-user.repository.ts
export class DynamoUserRepository implements IUserRepository {
  // DynamoDB-specific code lives ONLY here
}

// NestJS module — wires the concrete class to the interface token
// apps/users/user-api-service/src/modules/user.module.ts
{
  provide: USER_REPOSITORY,
  useFactory: (table: Table) => new DynamoUserRepository(table),
  inject: [DYNAMO_TABLE],
},
{
  provide: CreateUserUseCase,
  useFactory: (repo: IUserRepository) => new CreateUserUseCase(repo),
  inject: [USER_REPOSITORY],
},
Module 4

Domain Layer — The Heart

Entities, constants, and domain exceptions. This layer contains your business rules and invariants. It has zero framework dependencies.

What Lives Here?

📋 Constants

Enum-like objects for statuses and roles. Single source of truth — every layer references these, never raw strings.

domain/constants/user-statuses.ts

🏛 Entities

The business object with a private constructor, create() factory, reconstitute() factory, and business method for each state transition.

domain/entities/user.entity.ts

⚠️ Domain Exceptions

Typed errors that represent violations of business rules. They carry a human-readable message and are caught by the exception filter.

domain/exceptions/*.error.ts

Domain Constants — Single Source of Truth

Never use raw strings like 'ACTIVE' or 'ADMIN' anywhere in the codebase. Constants are defined once here and used everywhere via enum objects.

// packages/user-domain/src/domain/constants/user-statuses.ts

export const UserStatusEnum = {
  PENDING:  'PENDING',
  ACTIVE:   'ACTIVE',
  INACTIVE: 'INACTIVE',
  DELETED:  'DELETED',
} as const;

export type UserStatus = (typeof UserStatusEnum)[keyof typeof UserStatusEnum];

// Usage in any layer:
import { UserStatusEnum } from '@old-st/user-domain';
if (user.getUserStatus() === UserStatusEnum.ACTIVE) { ... }  // ✅
if (user.getUserStatus() === 'ACTIVE') { ... }               // ❌ never do this

The Entity Pattern

Every entity follows the same structure: private constructor (prevents invalid construction), a create() factory (for new objects), and a reconstitute() factory (for restoring from DB).

// packages/user-domain/src/domain/entities/user.entity.ts

export class User {
  // ① Private constructor — no one creates a User directly
  private constructor(
    private readonly userId: string | null,
    private readonly email: string,
    private firstName: string,
    private userStatus: UserStatus,
    private userRole: UserRole,
    private readonly dateCreated: string,
    private updatedAt: string
  ) {}

  // ② Factory: NEW user (validates input, sets initial state)
  static create(props: { email: string; firstName: string; lastName: string }): User {
    const emailRegex = /^[^\s@]+@[^\s@]+\.[^\s@]+$/;
    if (!emailRegex.test(props.email)) throw new InvalidEmailFormatError();
    if (props.firstName.trim().length === 0) throw new InvalidNameError('First name');

    const now = new Date().toISOString();
    return new User(
      null,                        // userId assigned by DB
      props.email.toLowerCase(),
      props.firstName.trim(),
      UserStatusEnum.PENDING,      // always starts PENDING
      UserRoleEnum.USER,
      now, now
    );
  }

  // ③ Factory: RECONSTITUTE from database (no validation)
  static reconstitute(props: { userId: string; email: string; /* ... */ }): User {
    return new User(props.userId, props.email, props.firstName, props.userStatus, /* ... */);
  }

  // ④ Business methods — each throws typed domain errors on invalid transitions
  activate(): void {
    if (this.userStatus !== UserStatusEnum.PENDING) {
      throw new CannotActivateNonPendingUserError();  // typed domain exception
    }
    this.userStatus = UserStatusEnum.ACTIVE;
    this.updatedAt = new Date().toISOString();
  }

  verifyEmail(): void {
    if (this.emailVerified) throw new EmailAlreadyVerifiedError();
    this.emailVerified = true;
    this.updatedAt = new Date().toISOString();
  }

  // ⑤ Query helpers
  isActive(): boolean  { return this.userStatus === UserStatusEnum.ACTIVE; }
  isDeleted(): boolean { return this.userStatus === UserStatusEnum.DELETED; }

  // ⑥ Getters — no public fields, controlled read access
  getUserId(): string | null { return this.userId; }
  getUserStatus(): UserStatus { return this.userStatus; }
  getEmail(): string { return this.email; }
}
✅ What Makes This "Clean"

The entity enforces business rules itself. activate() throws if the user isn't PENDING — you cannot build a use case that accidentally activates an already-active user. The business rule is co-located with the data.

⚠️ What NOT to Add to Entities
  • No toObject() or toJSON() — serialisation is the Application Service's job via Zod schemas
  • No NestJS decorators (@Injectable, @Column, etc.)
  • No database imports (@prisma/client, dynamodb-onetable)
  • No createdAt field — use dateCreated (OneTable manages createdAt internally)

Module 5

Application Layer — Use Cases

Use cases are the application-specific business rules. They orchestrate domain entities and call repository interfaces. They know nothing about HTTP, databases, or NestJS.

What Is a Use Case?

A use case represents one thing the user can do. It has a single execute(input) method. It receives its dependencies (repository, event publisher, ACL validator) via constructor injection.

📐 One Use Case = One File = One Folder

Each use case lives in its own folder: application/use-cases/create-user/create-user.use-case.ts. This makes the feature set immediately visible by browsing the folder structure.

// packages/user-domain/src/application/use-cases/create-user/create-user.use-case.ts

export class CreateUserUseCase implements IUseCase<CreateUserInput, User> {
  constructor(private readonly userRepository: IUserRepository) {}

  async execute(input: CreateUserInput): Promise<User> {
    // 1. Guard: application-level check (email uniqueness)
    const existingUser = await this.userRepository.findByEmail(input.email);
    if (existingUser) throw new EmailAlreadyExistsError(input.email);   // app exception

    // 2. Delegate to domain entity (which enforces its own invariants)
    const user = User.create({
      email: input.email,
      firstName: input.firstName,
      lastName: input.lastName,
      userRole: input.userRole ?? UserRoleEnum.USER,
    });
    // User.create() throws InvalidEmailFormatError or InvalidNameError if invalid

    // 3. Persist via repository interface (no DynamoDB knowledge here)
    return await this.userRepository.save(user);
    // Returns a domain User entity — NOT a DTO
  }
}

// apps/users/user-api-service/src/application/services/user-application.service.ts

@Injectable()
export class UserApplicationService {
  constructor(
    private readonly createUserUseCase: CreateUserUseCase,
    private readonly activateUserUseCase: ActivateUserUseCase,
    // ...all other use cases injected...
  ) {}

  // Entity → DTO (called after every use case that returns a User)
  private toDto(user: User): UserResponse {
    return userResponseSchema.parse({     // Zod validates on the way OUT too
      userId:      user.getUserId(),
      email:       user.getEmail(),
      firstName:   user.getFirstName(),
      userRole:    user.getUserRole(),
      userStatus:  user.getUserStatus(),
      dateCreated: user.getDateCreated(),
      updatedAt:   user.getUpdatedAt(),
    });
  }

  async createUser(input: CreateUserInput): Promise<UserResponse> {
    const user = await this.createUserUseCase.execute(input);  // returns domain entity
    return this.toDto(user);                                    // convert to DTO
  }

  async activateUser(userId: string): Promise<UserResponse> {
    const user = await this.activateUserUseCase.execute(userId);
    return this.toDto(user);
  }
}
✅ The Golden Rule

Domain entities never cross the presentation boundary. The controller only ever receives DTOs (plain objects validated by Zod), not domain entity instances. The Application Service is the hard wall between them.

Repository Implementation Pattern

Every repository follows the same pattern regardless of database: two private conversion methods (toDomain and toPersistence) plus the CRUD methods implementing the interface.

// packages/user-domain/src/infrastructure/repositories/dynamo-user.repository.ts

export class DynamoUserRepository implements IUserRepository {
  private readonly UserModel: IUserModel;

  constructor(private readonly table: Table) {
    this.UserModel = this.table.getModel('User') as unknown as IUserModel;
  }

  // ── Public methods (implement the interface) ────────────────────────
  async save(user: User): Promise<User> {
    const data = this.toPersistence(user);
    if (user.getUserId()) {
      const updated = await this.UserModel.upsert(data);   // existing user
      return this.toDomain(updated);
    } else {
      const created = await this.UserModel.create(data);   // new user
      return this.toDomain(created);
    }
  }

  async findById(userId: string): Promise<User | null> {
    const result = await this.UserModel.get({ userId });
    return result ? this.toDomain(result) : null;
  }

  async findByEmail(email: string): Promise<User | null> {
    // Uses GSI4 — email lookup never scans the whole table
    const results = await this.UserModel.find({ email }, { index: 'GSI4', limit: 1 });
    return results.length > 0 ? this.toDomain(results[0]) : null;
  }

  // ── Private converters — the ONLY code allowed to know DB record shape ──
  private toDomain(raw: UserDataType): User {
    const userId = raw.userId;
    if (!userId) throw new Error('DynamoDB record missing userId');
    return User.reconstitute({
      userId,
      email:         raw.email,
      firstName:     raw.firstName,
      lastName:      raw.lastName,
      emailVerified: raw.emailVerified ?? false,
      userRole:      raw.userRole as UserRole,
      userStatus:    raw.userStatus as UserStatus,
      dateCreated:   raw.dateCreated ?? new Date().toISOString(),
      updatedAt:     raw.updatedAt instanceof Date ? raw.updatedAt.toISOString() : raw.updatedAt,
      data:          raw.data || {},
    });
  }

  private toPersistence(user: User): Partial<UserDataType> {
    const userId = user.getUserId();
    return {
      ...(userId && { userId }),
      email:         user.getEmail(),
      firstName:     user.getFirstName(),
      lastName:      user.getLastName(),
      emailVerified: user.isEmailVerified(),
      userRole:      user.getUserRole(),
      userStatus:    user.getUserStatus(),
      dateCreated:   user.getDateCreated(),
      data:          user.getData(),
    };
  }
}
⚠️ No Business Logic in Repositories

Repositories only store and retrieve. Do not add validation, status checks, or business rules here. If you find yourself writing if (user.isActive()) in a repository, it belongs in a use case or entity instead.

Module 7

Presentation Layer — NestJS

Controllers, pipes, and filters. This is where HTTP meets your application. Controllers must be thin — delegate everything to the Application Service.

Validation Flow

// apps/users/user-api-service/src/presentation/controllers/user.controller.ts

@ApiTags('users')
@Controller('users')
export class UserController {
  constructor(private readonly userApplicationService: UserApplicationService) {}

  @Post()
  @HttpCode(HttpStatus.CREATED)
  createUser(
    // ZodValidationPipe validates & parses the body BEFORE it reaches the method
    @Body(new ZodValidationPipe(createUserSchema)) body: CreateUserInput,
  ) {
    // Controller is just a thin pass-through to the application service
    return this.userApplicationService.createUser(body);
  }

  @Post(':userId/activate')
  activateUser(@Param('userId') userId: string) {
    return this.userApplicationService.activateUser(userId);
  }

  @Get('by-status')
  listUsersByStatus(
    @Query(new ZodValidationPipe(listByStatusQuerySchema)) query: ListUsersByStatusInput,
  ) {
    return this.userApplicationService.listUsersByStatus(query);
  }

  // Health check — required by every service, must use @Public()
  @Get('health')
  @Public()
  health() {
    return { status: 'ok', service: 'user-api-service' };
  }
}

Exception Filter — Mapping Errors to HTTP

Domain and application exceptions are plain TypeScript errors. The DomainExceptionFilter catches them all and converts them to the correct HTTP status code.

// apps/users/user-api-service/src/presentation/filters/domain-exception.filter.ts

const DOMAIN_ERROR_MAP: Array<[ErrorConstructor, number]> = [
  [UserNotFoundError,                  404],
  [InvalidEmailFormatError,            400],
  [InvalidInputError,                  400],
  [EmailAlreadyExistsError,            409],
  [CannotActivateNonPendingUserError,  409],
  [CannotActivateUnverifiedEmailError, 409],
  [UserAlreadyDeletedError,           409],
  // ... all domain & application exceptions listed here
];

@Catch()
export class DomainExceptionFilter implements ExceptionFilter {
  catch(exception: unknown, host: ArgumentsHost): void {
    const response = host.switchToHttp().getResponse();

    // 1. NestJS HttpException (e.g. from ZodValidationPipe)
    if (exception instanceof HttpException) {
      const status = exception.getStatus();
      const res    = exception.getResponse();
      response.status(status).json(
        typeof res === 'string'
          ? { statusCode: status, error: exception.constructor.name, message: res }
          : res,
      );
      return;
    }

    // 2. Typed domain/application exceptions
    if (exception instanceof Error) {
      for (const [ErrorClass, statusCode] of DOMAIN_ERROR_MAP) {
        if (exception instanceof ErrorClass) {
          response.status(statusCode).json({
            statusCode,
            error:   exception.constructor.name,  // "EmailAlreadyExistsError"
            message: exception.message,
          });
          return;
        }
      }
    }

    // 3. Unexpected error — 500
    response.status(500).json({ statusCode: 500, error: 'InternalServerError', message: 'Unexpected error' });
  }
}
✅ Every new domain exception must be registered here

When you add a new exception class (e.g. CannotShipUnpaidOrderError), add it to DOMAIN_ERROR_MAP with the appropriate HTTP status. The use case just throws the typed error and the filter handles the rest.

Module 8

Golden Rules

These rules are enforced by ESLint, structural lint checks, and code review. Breaking them causes architectural drift that compounds over time.

The Non-Negotiable Rules

  • 1
    Controllers never call use cases directly. Always go through the Application Service. Controllers call this.userApplicationService.createUser(), never this.createUserUseCase.execute().
  • 2
    Application Services are always present. Even for a simple GET by ID. The Application Service is the boundary between presentation and domain — it must always exist, even as a thin pass-through.
  • 3
    Use Cases return domain entities. A use case returns User, not UserResponse. DTO transformation happens in the Application Service via userResponseSchema.parse().
  • 4
    Domain layer has zero framework dependencies. No import from @nestjs/*, dynamodb-onetable, @prisma/client, or any HTTP library. Pure TypeScript only. Enforced by structural lint check.
  • 5
    Domain constants are the single source of truth. Always use UserStatusEnum.ACTIVE, never the string 'ACTIVE'. Same for roles. Enforced by structural lint check entity-uses-enum-constants.
  • 6
    Never add toObject() to domain entities. Serialisation is the Application Service's job via Zod schema parse. Enforced by structural lint check entity-no-toObject.
  • 7
    Entity timestamps are dateCreated + updatedAt only. Never add a createdAt field to domain entities. OneTable auto-manages a persistence-level createdAt internally — the domain never sees it.
  • 8
    Infrastructure implements repository interfaces — no business logic, period. Repositories only store and retrieve. Business rules about state, validity, or workflow belong in the use case or entity, never in a repository.
  • 9
    Never import from the bare @old-st/contracts root. Always use domain-scoped subpaths: @old-st/contracts/user, @old-st/contracts/order. This prevents type coupling between domains. Enforced by structural lint check no-bare-contracts-import.
  • 10
    Check STAGE, not NODE_ENV, for local mode. NODE_ENV=production is correct locally (matches the webpack build). Use STAGE === 'local' to branch between LocalStack and AWS. Enforced by structural lint check no-node-env-development.

Contracts Package — Types at the Boundary

Contracts define the public interface of each domain: Zod schemas for request/response validation, TypeScript types, and re-exported domain constants. They live in packages/contracts/{domain}/ and are the only types that cross service boundaries.

// packages/contracts/user/src/schemas.ts
import { z } from 'zod';
import { UserStatusEnum, UserRoleEnum } from '@old-st/user-domain';

export const userResponseSchema = z.object({
  userId:      z.string(),
  email:       z.string().email(),
  firstName:   z.string(),
  lastName:    z.string(),
  userRole:    z.nativeEnum(UserRoleEnum),
  userStatus:  z.nativeEnum(UserStatusEnum),
  dateCreated: z.string(),
  updatedAt:   z.string(),
});

export type UserResponse = z.infer<typeof userResponseSchema>;
// Import in services — always use subpath:
import {
  userResponseSchema,
  UserResponse,
  createUserSchema,
  CreateUserInput,
} from '@old-st/contracts/user';  // ✅

// NEVER the bare root:
import { ... } from '@old-st/contracts'; // ❌

// NEVER from another domain's contracts:
import { UserResponse }
  from '@old-st/contracts/order'; // ❌

Adding a New Feature — Checklist

  1. 1
    Update contracts packages/contracts/{domain}/src/schemas.ts — add Zod schema for new input/output shape.
  2. 2
    Add/update entity method packages/{domain}-domain/src/domain/entities/{entity}.entity.ts — add business method with guard conditions and typed exceptions.
  3. 3
    Add domain exception packages/{domain}-domain/src/domain/exceptions/ — one file per exception class.
  4. 4
    Update repository interface if needed packages/{domain}-domain/src/application/interfaces/{entity}-repository.interface.ts — add new abstract method if a new query is required.
  5. 5
    Implement use case packages/{domain}-domain/src/application/use-cases/{action}/ — new folder + file, one file per use case.
  6. 6
    Update repository implementation packages/{domain}-domain/src/infrastructure/repositories/ — implement the new interface method with toDomain()/toPersistence().
  7. 7

Module 10

Frontend Clean Architecture

The same dependency-inversion principles that guide the backend apply to the frontend. Pages are thin orchestrators. Data access is layered. Business constants are never hardcoded strings.

The Frontend Layering Model

Just as the backend separates controllers from use cases from repositories, the frontend separates pages from components from hooks from API clients. Each layer has exactly one responsibility and only depends inward.

The Shared Data-Access Layer (@old-st/client-common)

The biggest win in the frontend architecture: a single package provides all data-fetching logic for both the Next.js webapp and the Expo mobile app. Neither app duplicates API calls or query cache logic.

🔌 infrastructure/api-clients/

One file per domain. Each method calls apiRequest() with a Zod schema. Responses are validated at the boundary — components always receive typed, valid data.

🪝 hooks/

React Query hooks wrapping each API client method. Queries have stable query keys. Mutations automatically invalidate the relevant cache keys on success.

⚙️ lib/providers.tsx

A single <Providers> component wraps QueryClientProvider + AuthProvider. Each app renders this as its root — zero boilerplate duplication.

🔑 infrastructure/config.ts

configureApi() sets domain API URLs once at app startup. Each app passes its own env vars (NEXT_PUBLIC_* vs EXPO_PUBLIC_*). The clients call getApiConfig().userApiUrl lazily.

The Base API Client — Single Source of HTTP Logic

All API calls funnel through one apiRequest() function. This means auth headers, silent token refresh, credentials: 'include', and Zod parsing are implemented once:

// packages/client-common/src/infrastructure/api-clients/base-api.client.ts

export async function apiRequest<T>(
  baseUrl: string,
  path: string,
  options?: { method?: string; body?: unknown; params?: Record<string, string | number | undefined>; schema?: ZodType<T> },
): Promise<T> {
  const token = accessTokenGetter?.();
  const url   = buildUrl(baseUrl, path, options?.params);

  let response = await fetch(url, {
    method:      options?.method ?? 'GET',
    credentials: 'include',                // always send httpOnly refresh cookie
    headers: {
      'Content-Type': 'application/json',
      ...(token ? { Authorization: `Bearer ${token}` } : {}),
    },
    ...(options?.body ? { body: JSON.stringify(options.body) } : {}),
  });

  // Silent token refresh on 401, then one retry
  if (response.status === 401 && onUnauthorized && !isRefreshing) {
    isRefreshing = true;
    const refreshed = await onUnauthorized().finally(() => { isRefreshing = false; });
    if (refreshed) response = await fetch(url, /* same options with new token */);
  }

  const data = await handleResponse(response);        // throws ApiError if !ok
  if (options?.schema && data !== undefined) {
    return options.schema.parse(data) as T;           // Zod validates at boundary
  }
  return data as T;
}
✅ Why This Matters

Components never think about Authorization headers, token refresh, or response shape. If the backend changes a field name, Zod throws at the API client boundary — not silently in a component rendering undefined.

Contracts — The Bridge Between Frontend and Backend

The same @old-st/contracts/{domain} packages used by NestJS controllers to validate outputs are used by frontend API clients to validate inputs. The Zod schema is literally the same object — one definition, two validation points.

A page component does three things only: manages local UI state, calls a hook, and renders child components. It has no table/form markup. Compare before and after:

Tables, rows, buttons, badges, and filters need data-testid attributes following the pattern {domain}s-table, {domain}-row-{id}, status-filter, create-{domain}-btn, {domain}-status-badge. These drive Playwright E2E tests.

Status Variant Mapping

Badge colours are driven by enum constants — never inline string comparisons. All mappings live in one file per platform:

// apps/webapp/src/lib/status-variants.ts
import { UserStatusEnum } from '@old-st/contracts/user';  // ✅ subpath import

type BadgeVariant = 'default' | 'secondary' | 'destructive' | 'outline' | 'success' | 'warning';

export function userStatusVariant(status: string): BadgeVariant {
  switch (status) {
    case UserStatusEnum.ACTIVE:   return 'success';      // 🟢
    case UserStatusEnum.PENDING:  return 'warning';      // 🟡
    case UserStatusEnum.INACTIVE: return 'secondary';    // ⚪
    case UserStatusEnum.DELETED:  return 'destructive';  // 🔴
    default:                      return 'outline';
  }
  // ❌ NEVER: case 'ACTIVE': return 'success';
}

export function UsersList({ users, isLoading }: { users: UserResponse[]; isLoading: boolean }) {
  if (isLoading && users.length === 0) {
    return <ActivityIndicator size="large" style={styles.loading} />;
  }
  return (
    // ✅ FlatList for virtualisation — never ScrollView + map()
    <FlatList
      data={users}
      keyExtractor={(item) => item.userId}
      renderItem={({ item }) => <UserListItem user={item} />}
      contentContainerStyle={styles.list}
      ListEmptyComponent={<Text variant="muted" style={styles.empty}>No users found</Text>}
    />
  );
}
