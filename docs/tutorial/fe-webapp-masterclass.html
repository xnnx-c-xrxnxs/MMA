Architecture Domain

Frontend CLEAN Architecture

The frontend applies the same Clean Architecture discipline as the backend: pages orchestrate, hooks fetch, API clients validate, UI primitives render. Each layer has a single responsibility. The dependency rule is enforced by convention and by the Golden Rules — pages never call fetch, hooks never render markup, API clients never own state.

L1 · Foundation
📋 Specification plain English
Architecture · Five Layers

The frontend stack has five layers, each with exactly one job:

  • Page — thin orchestrator. Wires hooks + domain components. Zero markup. Zero fetch calls. Zero useState.
  • Domain Component — renders one slice of domain data using @mma/ui primitives and React Query hooks.
  • React Query Hook — owns server state (loading, error, data, refetch). Calls one API client method.
  • API Client — typed fetch wrapper. Parses every response with a Zod schema from @mma/contracts/{domain}.
  • UI Primitive — stateless, domain-agnostic building block. Imports only design tokens and Tailwind classes.

The dependency rule: no layer may reach more than one level below it. A page never imports an API client. A hook never imports a UI primitive. An API client never imports a hook.

Shared contracts (@mma/contracts/{domain}) live outside this stack. They are imported at the boundary layers — by API clients (response validation) and by forms (Zod resolver) — and by the NestJS backend (ZodValidationPipe). One schema, two runtimes.

⚠️ Common pitfalls
  • Fetching in a page: calling fetch() or importing API clients directly from a page component breaks layer isolation — use a React Query hook instead.
  • Typing API responses manually: hand-writing type UserResponse = { ... } instead of importing from @mma/contracts/user causes the types to drift the moment the backend changes.
  • Reading process.env in components: env vars are configured once via configureApi() in layout.tsx — never read them inside a component or hook.
Architecture Domain

File Structure — New vs Old

The old template mixed all components into a shared library, used a flat route structure, and owned its own auth/layout wrappers per app. The new template uses Next.js App Router route groups, domain-scoped components co-located with pages, and a dedicated shared UI + data-access layer across web and mobile.

Old template (nx-template-v2):

  • Components live in libs/frontend/components-web/ — a shared lib used by all apps.
  • Data access in libs/frontend/data-access/src/api/ — Axios classes with inheritance.
  • Pages at apps/web-app/src/app/(authenticated-routes)/dashboard/.

  • Domain components co-locate with features in apps/webapp/src/components/{domain}/.

  • Auth guard is a useAuth() hook check in the (protected)/layout.tsx route group.
  • Styles: Tailwind v4 utilities + design tokens in packages/design-tokens/.

The key structural shift: domain knowledge stays with the app; primitives + data-access are shared packages.

Infrastructure Domain

Static Site Generation (SSG)

The old template required a running Node.js process (or a Lambda/ECS container) to serve each page request. The new template sets output: 'export' in next.config.js, which produces a static HTML + JS bundle under apps/webapp/out/ — deployed to S3 and served via CloudFront. No server, no cold starts, no container costs for the webapp.

L2 · Deployment
📋 Specification plain English
Infrastructure · Static Export

Old template: no output config → Next.js defaults to server rendering.

  • Requires a running Node.js process (ECS Fargate or Lambda container image).
  • Server-side redirects: async redirects() in next.config.js handle / → /auth/login.
  • Auth middleware runs server-side — can check cookies on the server before rendering.
  • Cost: always-on ECS task or Lambda warm-up on every page hit.

New template: output: 'export' → fully static bundle.

  • Build produces apps/webapp/out/ — plain HTML + CSS + JS files.
  • Synced to S3 + CloudFront: aws s3 sync out/ s3://bucket then CloudFront invalidation.
  • No server-side redirects: async redirects() is incompatible with static export. Auth guard moves to the client (useAuth() + useRouter() in the route group layout).
  • Edge middleware (middleware.ts) is also incompatible with static export — not used by default.
  • SPA routing: CloudFront returns index.html for all 403/404 responses so the client-side router handles deep links.
  • Cost: S3 storage + CloudFront data transfer only — no compute per page request.

Trade-off: no server-side rendering means auth protection is UX, not security. The API Gateway + NestJS JWT guards remain the true security boundary for every data request.

Infrastructure Domain

Data-Access Layer

The old template used an AxiosConfig base class that loaded environment variables asynchronously inside the constructor, applied interceptors for auth, and returned raw untyped response bodies. The new template replaces this with a single apiRequest<T>() function using the native fetch API — no Axios dependency, responses validated by Zod schemas from the shared contracts package, and a single configureApi() call at boot.

L3 · Data Access
📋 Specification plain English
Data Access · API Clients

Old approach — Axios class inheritance:

  • AxiosConfig base class reads env vars via an async getEnv() inside the constructor — env is not available synchronously at class creation time.
  • Each API service creates a subclass: class AuthApi extends AxiosConfig.
  • Axios interceptors handle token injection and 401 redirects.
  • Response bodies are returned as any — no runtime validation.
  • Depends on the axios and js-cookie packages.

New approach — apiRequest<T>() + Zod:

  • configureApi() is called once in layout.tsx — synchronous, no async constructor issues.
  • apiRequest<T>() is a plain async function using native fetch — zero new dependencies.
  • Every API client method passes a schema: ZodType<T> option — the response is parsed and typed at the boundary.
  • A 401 triggers a silent token refresh; if refresh fails, the user is signed out.
  • The same clients work on both the webapp and the Expo mobile app (no browser globals).

import { type ZodType } from 'zod';
import { ApiError } from '../errors/api-error';

// ── Token management ─────────────────────────────────────────────────────
let accessTokenGetter: (() => string | null) | null = null;
let onUnauthorized: (() => Promise<boolean>) | null = null;
let isRefreshing = false;

export function setAccessTokenGetter(getter: () => string | null): void {
  accessTokenGetter = getter;
}
export function setOnUnauthorized(handler: () => Promise<boolean>): void {
  onUnauthorized = handler;
}

// ── Core request function ─────────────────────────────────────────────────
export async function apiRequest<T>(
  baseUrl: string,
  path: string,
  options?: {
    method?: string;
    body?: unknown;
    headers?: Record<string, string>;
    params?: Record<string, string | number | undefined>;
    schema?: ZodType<T>;          // ← Zod schema validates the response at runtime
  },
): Promise<T> {
  const { method = 'GET', body, headers, params, schema } = options ?? {};

  // Build URL with optional query parameters
  const url = new URL(`${baseUrl}${path}`);
  if (params) {
    for (const [key, value] of Object.entries(params)) {
      if (value !== undefined) url.searchParams.set(key, String(value));
    }
  }

  // Attach the in-memory access token (never read from localStorage)
  const token = accessTokenGetter?.();
  const authHeaders: Record<string, string> = token
    ? { Authorization: `Bearer ${token}` }
    : {};

  let response = await fetch(url.toString(), {
    method,
    credentials: 'include',           // sends httpOnly refresh cookie
    headers: { 'Content-Type': 'application/json', ...authHeaders, ...headers },
    body: body !== undefined ? JSON.stringify(body) : undefined,
  });

  // Silent token refresh on 401
  if (response.status === 401 && !isRefreshing && onUnauthorized) {
    isRefreshing = true;
    const refreshed = await onUnauthorized();
    isRefreshing = false;
    if (refreshed) {
      const newToken = accessTokenGetter?.();
      response = await fetch(url.toString(), {
        method,
        credentials: 'include',
        headers: {
          'Content-Type': 'application/json',
          ...(newToken ? { Authorization: `Bearer ${newToken}` } : {}),
          ...headers,
        },
        body: body !== undefined ? JSON.stringify(body) : undefined,
      });
    }
  }

  if (response.status === 204) return undefined as T;

  const responseBody = await response.json().catch(() => null);
  if (!response.ok) {
    throw new ApiError(
      response.status,
      responseBody?.error ?? response.statusText,
      responseBody?.message ?? 'An unexpected error occurred',
    );
  }

  // ✅ Zod parse validates the shape BEFORE returning to the hook
  return schema ? schema.parse(responseBody) : (responseBody as T);
}

Authentication Domain

Auth Flow — Tokens & Cookies

The old template stored tokens in cookies readable by JavaScript (js-cookie) and loaded them at component render time. The new template follows the secure browser token pattern: the refresh token lives in an httpOnly cookie (unreadable by JS), the access token lives only in memory (lost on reload, restored by silent refresh), and a single useAuth() hook from client-common manages the full lifecycle.

L4 · Security
📋 Specification plain English
Authentication · Token Rules

Old template auth risks:

  • Tokens stored in js-cookie — readable from JavaScript → XSS risk.
  • Session ID in a cookie: Cookies.get(STORAGE_KEY.SESSION_ID).
  • Auth state duplicated: cookie + React Context + Axios interceptor.
  • No silent refresh — user hit 401 and saw an error.
  • ProtectedRoute component had to know the auth implementation.

New template secure flow (Golden Rules #24–#28):

  • Refresh token → httpOnly, Secure, SameSite cookie — JS cannot read it.
  • Access token → in-memory only (setAccessTokenGetter() in AuthProvider).
  • On page load: POST /auth/refresh-session with credentials: 'include' restores the session silently.
  • On 401: apiRequest calls onUnauthorized() → refresh → retry automatically.
  • All API calls use credentials: 'include' so the browser sends the httpOnly cookie.
  • CORS: backend sets origin: process.env.FE_BASE_URL, credentials: true — never origin: '*'.

Security boundary reminder: client-side auth is UX only. Every data endpoint validates the JWT at the API Gateway + NestJS guard level.

import React, { createContext, useContext, useState, useEffect, useCallback } from 'react';
import { refreshSession, signIn as apiSignIn, signOut as apiSignOut } from '../infrastructure/api-clients/auth-api.client';
import { setAccessTokenGetter, setOnUnauthorized } from '../infrastructure/api-clients/base-api.client';

interface AuthState {
  isAuthenticated: boolean;
  isLoading: boolean;
  userId: string | null;
  email: string | null;
}

const AuthContext = createContext<AuthState & {
  signIn: (email: string, password: string) => Promise<void>;
  signOut: () => Promise<void>;
} | null>(null);

export function AuthProvider({ children }: { children: React.ReactNode }) {
  const [state, setState] = useState<AuthState>({
    isAuthenticated: false,
    isLoading: true,    // true until silent refresh resolves
    userId: null,
    email: null,
  });

  // Access token stored in a closure — never in localStorage or a cookie
  let accessToken: string | null = null;

  // Register the getter with the base API client
  useEffect(() => {
    setAccessTokenGetter(() => accessToken);
    setOnUnauthorized(async () => {
      try {
        const res = await refreshSession();  // uses httpOnly cookie
        accessToken = res.accessToken;
        setState({ isAuthenticated: true, isLoading: false, userId: res.userId, email: res.email });
        return true;
      } catch {
        accessToken = null;
        setState({ isAuthenticated: false, isLoading: false, userId: null, email: null });
        return false;
      }
    });
  }, []);

  // ── Restore session on cold load ──────────────────────────────────────
  useEffect(() => {
    refreshSession()
      .then(res => {
        accessToken = res.accessToken;
        setState({ isAuthenticated: true, isLoading: false, userId: res.userId, email: res.email });
      })
      .catch(() => {
        setState(s => ({ ...s, isLoading: false }));  // not authenticated, stop spinner
      });
  }, []);

  const signIn = useCallback(async (email: string, password: string) => {
    const res = await apiSignIn(email, password);
    if (res.type === 'SUCCESS') {
      accessToken = res.accessToken;
      setState({ isAuthenticated: true, isLoading: false, userId: res.userId, email: res.email });
    }
    // Discriminated union: other types (NEW_PASSWORD_REQUIRED etc.) handled by caller
    return res;
  }, []);

  const signOut = useCallback(async () => {
    await apiSignOut();
    accessToken = null;
    setState({ isAuthenticated: false, isLoading: false, userId: null, email: null });
  }, []);

  return (
    <AuthContext.Provider value={{ ...state, signIn, signOut }}>
      {children}
    </AuthContext.Provider>
  );
}

// ✅ Single hook consumed by every component that needs auth state.
// Zero knowledge of httpOnly cookies, Axios interceptors, or session storage.
export function useAuth() {
  const ctx = useContext(AuthContext);
  if (!ctx) throw new Error('useAuth must be used inside <AuthProvider>');
  return ctx;
}

⚠️ Common pitfalls
  • Using yupResolver in a new form: the old template used yup — if you copy a form from the old codebase, swap yupResolver for zodResolver and replace the yup schema with the corresponding import from @mma/contracts/{domain}.

Component API Patterns & Tailwind v4

The old template styled components with SCSS modules alongside scattered Tailwind classes, and used a flat prop-driven component API. The new template uses inline Tailwind v4 utilities exclusively, configured with a CSS-first approach (no tailwind.config.js), and separates component concerns into two tiers: a flexible compound API for the primitive and a thin convenience wrapper for everyday app usage.

Component Design · Three Topics

1 · Compound vs Simple API

The old template used a flat prop-driven API — one component, many props (isOpen, title, showClose, footerActions…). This is fast initially but becomes bloated as requirements grow.

The new template follows the compound component pattern from shadcn/Radix as the base primitive, then adds a thin convenience wrapper for common app usage:

  • Base primitive — Modal, ModalTrigger, ModalContent, ModalHeader, ModalBody, ModalFooter (full composability, zero layout constraints).
  • Convenience wrapper — AppModal accepts isOpen, title, onClose, children and optional actions. Used in 80 % of app screens.
  • Feature pages use AppModal; unusual dialogs (multi-step, custom footer) drop down to the compound primitive.

✅ Simple / prop-driven — pros

  • Minimal boilerplate — one import, one JSX element
  • Easy to discover — all options visible in TypeScript autocomplete
  • Fast for beginners — no knowledge of sub-components needed
  • Controlled state (isOpen) works well out of the box

❌ Simple / prop-driven — cons

  • Props accumulate — every new layout requirement adds a boolean (hideHeader, showDivider…)
  • Conditional rendering logic leaks into the component internals
  • Impossible to reorder or rearrange sections without new props
  • Testing grows harder as prop combinations multiply

✅ Compound + wrapper — pros

  • Zero prop explosion — new layouts compose sub-components, never add props
  • Each sub-component is independently testable and styleable
  • Wrapper (AppModal) keeps everyday usage just as simple as the prop-driven pattern
  • Accessible by default — Radix manages focus trap, ARIA roles, keyboard nav
  • Inversion of control — caller owns the layout, not the component

❌ Compound + wrapper — cons

  • More files — primitive + wrapper + types instead of one component
  • Higher learning curve — caller must understand the sub-component tree
  • Context coupling — sub-components only work inside their parent root (<Modal>)
  • Over-engineering risk for truly simple, never-changing UI elements

2 · Inline Tailwind vs SCSS Modules

The old template co-located a .module.scss for every component, then also added Tailwind utility classes into the SCSS (@apply) — two systems at once, neither owning the truth.

Why inline Tailwind wins:

  • Single source of truth — style is on the element, not in a separate file you have to open.
  • No context-switch — designer, reviewer, and AI all see the styling without leaving the component.
  • No dead CSS — deleting a component deletes its styles; SCSS files linger.
  • Tokens enforced — Tailwind utility classes map to the design-token layer automatically; ad-hoc colour values are impossible without [] escape hatch, which is immediately visible in review.
  • Dark mode in one place — dark:bg-card sits next to bg-card on the element; no .dark block in a remote SCSS file.
  • Build output — Tailwind v4's JIT emits only the classes present in source; @apply in SCSS bypassed the scanner, causing larger CSS output.

3 · Tailwind v4 Setup — CSS-First (No tailwind.config.js)

Tailwind v4 replaces the JS config file with a CSS-first approach. All tokens, source paths, and plugin config live in globals.css.

  • Old: tailwind.config.js with content: [...], theme.extend and plugins.
  • New: @import "tailwindcss" at the top of globals.css; tokens in @theme { --color-primary: ... }; dark overrides in .dark { --color-primary: ... }; source paths via @source "../../packages/ui/src".

Result: one file owns all styling configuration — easier to audit, diff, and share with designers.

Step 1 · Import Design Tokens

Tokens are the contract between the designer and the codebase. They must be set up before any component is written — otherwise the first component hard-codes a hex value that you will chase forever.

  1. Export tokens from Figma — use the Figma Tokens / Variables plugin to export a JSON of all colour, spacing, radius, and typography values. Save as packages/design-tokens/src/lib/tokens.ts.
  2. Define lightColors and darkColors — two typed maps (see code panel). Mobile imports them directly; web consumes them via CSS variables.
  3. Generate tokens.css — run pnpm tokens:gen. This script writes :root { --color-primary: ... } and .dark { --color-primary: ... } blocks from the TypeScript maps.
  4. Import in globals.css — add @import "@mma/design-tokens/tokens.css" above the @theme {} block. Tailwind v4 reads the CSS variables and exposes them as utilities (bg-primary, text-foreground, etc.).
  5. Verify — open any page; all bg-* and text-* utilities resolve without warnings. Toggle dark mode — colours swap without any JavaScript.

Rule: no raw hex or rgb() values anywhere in component files. If a colour is not in the token map, add it to the token map first — then use the utility class.

Step 2 · Convert SVG to Typed Icon Components

Raw SVG files scattered in public/ or inlined in components are not tree-shaken, not typed, and cannot be themed. Convert them once into typed React components before any component imports an icon.

  1. Export SVGs from Figma — select all icons on the icon frame, export at 1× as SVG (no effects, no extra wrappers). Name files in kebab-case: arrow-right.svg, check-circle.svg.
  2. Run SVGR — pnpm svgr --icon --typescript --out-dir packages/ui/src/components/icons/generated src/assets/icons/. Each SVG becomes a ArrowRightIcon.tsx exporting a standard React component that accepts className and size.
  3. Define the IIcon interface — a shared prop contract for all icon components (see code panel). This makes every icon interchangeable — a component that accepts icon: IIcon works with any icon from the set.
  4. Barrel-export from packages/ui/src/components/icons/index.ts — one export per icon so consumers import precisely what they use: import { ArrowRightIcon } from '@mma/ui'.
  5. Theme icons with currentColor — SVGR replaces hard-coded fills with fill="currentColor" automatically. Set colour via className="text-primary" on the icon element — it inherits from the parent.

Rule: never copy SVG markup into a component. Never use <img src="icon.svg"> for UI icons — images are not themeable and not accessible without extra aria attributes.

Step 3 · Implement Figma Components

With tokens and icons in place, every Figma component can be faithfully implemented. Work primitives-first: shared building blocks before domain-specific pages.

  1. Classify components — open the Figma file, identify which frames are primitives (Button, Badge, Card, Input, Select, Modal…) and which are page sections (UserTable, CreateOrderForm…). Primitives go in packages/ui/; page sections go in apps/webapp/src/components/{domain}/.
  2. Run /figma-component workflow for each primitive — paste the Figma URL → Claude Code fetches get_design_context, maps visual properties to token utilities, and scaffolds the component file with cva() variants, a Storybook story, and a Jest spec.
  3. Map tokens explicitly — for each fill, stroke, and spacing value the design context returns, confirm it matches a token in tokens.ts. If it does not match, add the token first (Step 1), then use the utility class. Never accept a raw hex value in generated code.
  4. Wire the IIcon interface where icons appear — if a Figma component shows an icon slot, type it as icon?: IIcon and render {icon && <icon className="..." />}. This keeps the component decoupled from any specific icon.
  5. Run /figma-page workflow for each screen — after all required primitives exist, port each Figma screen to a Next.js page. The workflow decomposes the screen into sections and maps each section to existing primitives. It will flag any missing primitive and recurse into /figma-component before continuing.
  6. Verify tokens round-trip — inspect the rendered page in the browser and compare against the Figma design. Open the design-preview route (/design-preview) to confirm all token values match the Figma variables export.

Why this order? Tokens first means every component created in Steps 2–3 automatically inherits dark mode and theming. Icons second means the Figma component workflow in Step 3 can reference a typed IIcon slot instead of inlining SVG. Primitives before pages means there is never a moment when a page component depends on a primitive that does not yet exist.

⚠️ Common pitfalls
  • Don't write components before the token pipeline is live. The first component that uses bg-[#4f46e5] creates a precedent — every component after it will do the same. Tokens first, always.
  • Don't regenerate tokens by hand. Run pnpm tokens:gen after any change to tokens.ts. The CSS file is generated output — it should never be edited directly.
  • Don't import darkColors in webapp components. Web components use Tailwind utilities (dark:bg-card); only mobile imports darkColors directly from @mma/design-tokens. Importing the TS map in a web component bypasses the CSS variable layer.
  • Don't inline SVGR output as JSX in a component file. Run the CLI once, commit the generated files, then import from the icons barrel. Re-run the CLI whenever icons change — regenerating is idempotent.
  • Don't implement Figma pages before all required primitives exist. The /figma-page workflow will flag missing primitives — complete those first via /figma-component, then continue. Skipping this produces page components that duplicate primitive logic.
  • Don't accept raw hex values from get_design_context output. The design context returns loosely structured code as a reference. Every colour must map to a token utility. If a colour is not in the token map, add it before wiring the component.
