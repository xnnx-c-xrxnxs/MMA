Module 2 — 30 min

Vibe Coding vs Spec-Driven Development

Two ways to build with AI. One is great for exploration. The other is how you ship production code. Know when to use each.

What is Vibe Coding?

Conversational, ad-hoc prompting with minimal structure or specification. You describe what you want in natural language and hope for the best.

“Vibe coding is like giving a contractor verbal instructions with no blueprints.”

✅ When It Works

  • Prototyping and proof-of-concept
  • Throwaway scripts and one-off utilities
  • Learning a new language or framework
  • Hackathons and rapid exploration
  • Personal side projects

❌ When It Fails

  • Team inconsistency — 5 devs, 5 different patterns
  • Architectural drift — AI doesn’t know your clean architecture rules
  • Silent defects — code looks correct but violates invariants
  • No reproducibility — same prompt, different day, different output
  • Security gaps — AI doesn’t know your OWASP requirements

What is Spec-Driven Development?

Development guided by structured, machine-readable specifications that define architecture, constraints, patterns, and validation rules. The AI follows your engineering system, not its own defaults.

The “Spec” Consists Of:

CLAUDE.mdArchitecture, golden rules, patterns, conventions1,000+ lines
.claude/skills/Focused instructions for specific task types40 skills
.claude/commands/Multi-phase guided workflows6 orchestrators
AGENTS.mdGlobal agent behavior rules~30 lines
Key Principle

“The quality of AI output is directly proportional to the quality of your specification.”

🎤 Speaker Notes
You write the spec once. Every developer on the team benefits. Every AI interaction is governed by the same standard. One senior’s work scales to the entire team.

Smart Prompting for Developers

The C.I.C.F. Framework

C — Context

What are you working on? What files/patterns are relevant?

I — Intent

What do you want to accomplish?

C — Constraints

Rules, patterns, architectures to follow.

F — Format

How you want the output structured.

AI Safety & Security

⚠️ Non-Negotiable Rules

Rule 1: Never blindly trust AI for security-sensitive code (auth, crypto, SQL, file I/O).
Rule 2: Code review is MORE important with AI, not less.
Rule 3: Never paste API keys, customer data, or proprietary algorithms into prompts.
Rule 4: AI doesn’t know your business rules unless you tell it.

The “Rubber Stamp” Anti-Pattern

AI-generated code has the same bug rate or higher than human code. It just looks more polished, which makes reviewers less careful. Review AI code with MORE scrutiny, not less.

Use Case 1: Creating a Domain Entity

Manual effort ~30 min
AI with spec-driven ~3 min

The Prompt

Spec-Driven 
Create a domain entity Order for the order-domain package.
- Private constructor, create() factory, reconstitute() factory
- Properties: orderId, customerId, items[], payment,
  orderStatus, totalAmount, dateCreated, updatedAt
- create() sets status to DRAFT via OrderStatusEnum,
  validates customerId is not empty
- addItem() throws CannotModifyNonDraftOrderError if not DRAFT
- Use domain constants for all status comparisons

AI Output (from our codebase)

export class Order {
  private constructor(
    private readonly orderId: string | null,
    private customerId: string,
    private items: OrderItem[],
    private payment: OrderPayment | null,
    private orderStatus: OrderStatus,
    private totalAmount: number,
    private readonly dateCreated: string,
    private updatedAt: string
  ) {}

  static create(props: { customerId: string }): Order {
    if (!props.customerId.trim()) {
      throw new CustomerIdRequiredError();
    }
    const now = new Date().toISOString();
    return new Order(
      null, props.customerId, [], null,
      OrderStatusEnum.DRAFT, // ← Enum constant, not 'DRAFT' string
      0, now, now
    );
  }

  addItem(item: OrderItem): void {
    if (this.orderStatus !== OrderStatusEnum.DRAFT) {
      throw new CannotModifyNonDraftOrderError('add');
    }
    this.items.push(item);
    this.recalculateTotal();
    this.updatedAt = new Date().toISOString();
  }
  // ... getters, reconstitute(), other state transitions
}
What AI Got Right (Because of Specs)
  • Private constructor — enforced by new-domain-entity skill
  • Factory methods create() + reconstitute() — pattern from skill instructions
  • Enum constants (OrderStatusEnum.DRAFT) — Golden Rule #8, never hardcode strings
  • Typed domain exceptions — not generic Error, mapped to HTTP 409
  • Immutable orderId — readonly, null until persisted
🎤 Speaker Notes
Without spec context, Claude Code would generate a simple class with public properties, no factory methods, string literals for status, and generic Error throws. The spec-driven version follows every Golden Rule automatically.

Use Case 2: Business Logic with Cross-Service Validation

Manual effort ~45 min
AI with spec-driven ~5 min

The Prompt

Spec-Driven 
Add a CreateOrder use case to order-domain.
- Validates customer exists and is active via
  ICustomerValidator (ACL — cross-service call)
- Creates Order entity, adds items from input
- Saves to IOrderRepository
- Publishes ORDER_CREATED event via IEventPublisher

AI Output

export class CreateOrderUseCase implements IUseCase<CreateOrderInput, Order> {
  constructor(
    private readonly orderRepository: IOrderRepository,
    private readonly customerValidator: ICustomerValidator,
    private readonly eventPublisher: IEventPublisher<unknown>,
  ) {}

  async execute(input: CreateOrderInput): Promise<Order> {
    // Application-level validation
    if (!input.customerId) {
      throw new InvalidInputError('Customer ID is required');
    }
    if (!input.items || input.items.length === 0) {
      throw new InvalidInputError('At least one item is required');
    }

    // ACL: Cross-service validation (Order → User API)
    await this.customerValidator.validate(input.customerId);

    // Domain: Create entity + add items
    const order = Order.create({ customerId: input.customerId });
    for (const itemInput of input.items) {
      const item = OrderItem.create({
        productId: itemInput.productId,
        productName: itemInput.productName,
        quantity: itemInput.quantity,
        price: itemInput.price,
      });
      order.addItem(item);
    }

    // Persist + publish event
    const savedOrder = await this.orderRepository.save(order);
    await this.eventPublisher.publish({
      type: OrderEventType.ORDER_CREATED,
      payload: { orderId: savedOrder.getOrderId() },
    });

    return savedOrder;
  }
}

🔌 ACL Pattern

ICustomerValidator is an abstract interface in order-domain. The HTTP adapter (UserApiClient) lives in the service’s infrastructure/clients/. The use case never sees HTTP, Axios, or user-domain types.

📤 Event Publishing

IEventPublisher is injected — the use case doesn’t know it’s SQS. The adapter (SqsStandardEventPublisher) is wired in the NestJS module.

🏗️ Clean Boundaries

The use case depends only on interfaces. Repository, ACL validator, and event publisher are all injected. Infrastructure knows about Prisma/SQS/HTTP; the use case doesn’t.

Supporting Services — Auth & File Upload

Two cross-cutting services sit alongside the core domain services. They are never called directly by domain services — they provide capabilities consumed by API clients and orchestrated through the shared frontend layer.

ServicePortResponsibility
auth-api-service 3003 Sign-in, refresh, password flows. Uses IAuthProvider abstraction: CognitoAuthProvider in deployed environments, LocalAuthProvider in development (admin@test.com / Password123!).
file-api-service 3004 Presigned S3 URL gateway. Clients upload directly to S3 — no file bytes pass through the backend. Domain services store only a fileKey.

Auth: Provider Abstraction Pattern

// Deployed: delegates to AWS Cognito SDK
class CognitoAuthProvider implements IAuthProvider { ... }

// Local (STAGE=local): accepts admin@test.com / Password123!
// Issues unsigned mock JWTs. No Cognito dependency in dev.
class LocalAuthProvider implements IAuthProvider { ... }

// JwtAuthGuard is provider-agnostic — reads env vars:
//   JWT_JWKS_URI    → JWKS endpoint for token verification
//   JWT_ISSUER      → expected issuer claim
//   JWT_USER_ID_CLAIM → claim name holding userId (e.g. "sub")
// Locally bypassed when STAGE=local.

File Upload: Presigned URL Flow

// 1. Client requests a presigned upload URL
POST /api/files/presigned-upload
  → { uploadUrl, fileKey, expiresIn }

// 2. Client uploads directly to S3 (no backend involved)
PUT {uploadUrl} (binary file body)

// 3. Domain service stores only the fileKey
// Never store the full S3 URL — only the key
const order = Order.create({ ..., attachmentKey: fileKey });

// 4. Download: request a presigned download URL
GET /api/files/presigned-download/{key}
  → { downloadUrl, expiresIn }
Golden Rule: File bytes never pass through the backend

Domain services must never import from aws-s3 or call S3 directly. Only file-api-service touches S3. Domain entities store a fileKey string. This keeps Lambda payload sizes small and prevents timeouts on large uploads.

  return useMutation({
    mutationFn: (input: CreateUserInput) =>
      userApiClient.create(input),
    onSuccess: () => {
      queryClient.invalidateQueries({ queryKey: [USERS_KEY] });
    },
  });
}

export function useDeleteUser() {

  return useMutation({
    mutationFn: (userId: string) => userApiClient.delete(userId),
    onSuccess: () => {
      queryClient.invalidateQueries({ queryKey: [USERS_KEY] });
    },
  });
}

🔒 Type-Safe End-to-End

Zod schema parses the API response at runtime. TypeScript infers the return type from the schema. No as any, no manual type casting.

🧹 Automatic Cache Invalidation

Every mutation invalidates the USERS_KEY queries. The UI refreshes automatically — no manual fetch calls.

📦 Shared by Web + Mobile

These hooks and clients live in @mma/client-common. Both the Next.js webapp and Expo mobile app import them. Zero duplication.

Authentication: Silent Refresh + Memory-Only Access Tokens

Access tokens are stored in memory only — lost on page refresh and restored via silent refresh: the AuthProvider in client-common calls POST /auth/refresh-session on mount with credentials: 'include' to restore the session from the httpOnly refresh cookie. Frontend code never reads the refresh token. On 401, the client retries once after attempting a silent refresh. Refresh tokens are stored in httpOnly cookies — never in localStorage.

Your Task

“Add a ‘suspend’ action to the user entity. A user can only be suspended if they are currently ACTIVE. Suspended users cannot log in.”

What to Observe

  • Does Claude Code ask clarifying questions? (It should, if using the command)
  • Does it follow our architecture? (Entity → Use Case → App Service → Controller)
  • Does the generated code use enum constants? (Not string literals)
  • Does it add proper domain exceptions?

Debrief: Compare results across the room. Discuss what worked and what didn’t.
